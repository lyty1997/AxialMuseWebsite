# Issue 编写与拆解

适用于新模块、跨层契约和复杂任务；纯文档或单文件小修可豁免。本规则只约束任务执行方式，不替代 `docs/` 中的专项设计，也不构成创建或修改 GitHub Issue、PR 等外部资源的授权。

## 开工前

Issue / 任务必须写成可执行验收项：

- 对外接口签名或 route / event；
- 字段、类型、必填性、枚举、错误码和结构；
- tenant / revision / trace / 关联 ID 等跨层字段由谁注入；
- 上下游依赖、设计真相源、风险和完成标准。

上下游未就绪时，用 mock / stub / fixture 证明正常路径和至少一个异常 / 边界路径；保留可复现的输入 → 输出证据。没有证据不能标 Done。

## 复杂任务

跨多模块、状态多或一次无法闭环时，先拆成可独立验收的子任务，标明 blocks / blocked-by，再按依赖顺序逐个完成。父 Issue 只汇总范围与里程碑，避免多个半成品并行堆积。

### 标准颗粒度

一个子任务只承诺：**一个主要不变量 + 一套独立验收证据**。

- 主要不变量必须能用一句可证伪的话描述清楚：给定什么输入或前置状态，系统必须保持什么性质，违反时如何 fail-loud。若一句话包含两个可分别通过、失败或回滚的同级“并且”，继续拆分。
- 独立验收是指：只完成已声明的 `blocked-by` 后即可运行，不依赖尚未完成的后续兄弟任务。可以使用 mock / stub / fixture，但必须证明当前不变量本身，不得以“等端到端完成后一起测”代替。
- 每套证据至少包含一个正常路径和一个会让错误实现变红的异常、边界或反例。正确性 / 安全门禁优先增加 golden、metamorphic（变形关系）或定向 mutation 证据，证明测试不是只覆盖当前实现表面。
- 证据层级与不变量匹配：纯算法用手算 golden / 性质测试；持久化不变量检查事务、约束和失败残留；对外命令或 API 检查真实入口、稳定错误码和小结果包。无需为了“纵向切片”强迫纯算法子任务提前接 CLI。

出现下列任一情况时通常应继续拆分：

- 使用不同真相源、状态机或事务边界；
- 一个性质通过时，另一个仍可独立失败；
- 验收需要明显不同的 fixture 或运行环境，例如纯函数 golden 与 PostgreSQL / CLI 实跑；
- 一部分可以独立评审、回滚或复用；
- 当前子任务无法在后续兄弟任务完成前给出关闭证据。

不要按文件、目录、技术层或 helper 数量机械拆分。为证明同一不变量所需的 DTO、Repository、Service 和入口接线可以留在同一子任务；共享同一引擎和验收性质的一组因子也不按“一个因子一个 Issue”拆散。

### 子任务必填项

每个子任务至少写明：

- **主要不变量**：一句话，只放一个判定中心；
- **范围 / 非范围**：本项写什么，以及明确不抢跑什么；
- **blocked-by / blocks**：依赖到可运行证据的最小集合；
- **验收证据**：fixture、命令、关键断言、正常路径和反例；
- **完成与关闭证据**：实际命令、结果、必要的脱敏输出，以及对应实现 / 测试位置。

### 批量推进与上下文交接

父任务的设计、拆解和验收标准经用户确认后，主执行者应按 `blocked-by` 顺序自主推进各子任务；只要没有改变已确认设计、扩大范围、触发新的外部写操作或遇到需要用户裁决的分歧，不要求用户逐项重复确认。

每个子任务完成后必须形成一份紧凑的交接摘要，至少记录：

- 已建立的主要不变量，以及违反时的稳定失败形态；
- 新增或改变的公开接口、数据模型、事务边界和跨层字段；
- 关键实现 / 测试位置与实际验收命令、结果；
- 相对设计或 Issue 的偏差、已作出的决定和仍未消除的风险；
- 下一个子任务真正需要继承的输出、前置条件和禁止重新解释的约束。

交接摘要先写入当前执行计划；任务可能跨会话、接近上下文上限或需要多人协作时，同步到父 / 子 Issue、PR 描述或项目既有进度台账。摘要只负责索引和恢复现场，不能取代专项设计、代码、迁移、机器可读契约与测试这些真相源。

启动下一个子任务时执行一次**语义压缩与定向重载**：只装载父任务目标、当前不变量与验收标准、直接上游交接摘要、相关真相源、当前源码 / 测试和工作区 diff；不为“保持完整”无差别重读所有已完成子任务的过程记录。平台级上下文压缩由运行环境自动触发，不能假定可手动控制；无论是否发生平台压缩，都必须能依靠持久化真相源和交接摘要恢复现场。

### 主执行者与 subagent 分工

- 默认由一个主执行者连续持有父任务架构、共享契约和生产代码集成责任，避免多个代理分别解释同一接口、状态机或事务语义。
- subagent 仅在能力可用且任务边界独立时使用，优先承担只读复核、测试盲区 / mutation 检查、文档一致性检查，或不改写共享契约的独立实现；存在 `blocked-by`、共享数据模型或同一原子提交边界的子任务不得为追求并行而强行分发。
- subagent 的结论不是关闭证据。主执行者必须亲自检查其产出与 diff，核对设计和错误形态，并运行当前子任务的独立验收；不能仅凭代理报告标 Done。
- 全部子任务完成后，主执行者恢复父任务视角，检查跨子任务接口、最短端到端链和全量回归，再决定父 Issue 是否可关闭。

父 Issue 只有在全部子任务各自闭环、按真实依赖串起最短集成链后才能关闭；不能用父 Issue 的一次全量绿替代某个子任务缺失的定向证据。

## 收尾

在 Issue / PR 留下命令、结果和必要的脱敏证据；跨模块结果同步到项目验证或进度台账。Issue 中的建议方案不是事实，实现前仍须用当前设计、代码和复现验证。
