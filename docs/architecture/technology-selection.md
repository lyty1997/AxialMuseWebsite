## 决策摘要

M0 主站采用语义化 HTML5、原生 CSS 和本地静态资源，不引入前端框架、运行时 JavaScript、组件库、CSS 预处理器、CMS、数据库或第三方字体。Node.js 22 只用于仓库质量门禁；生产环境由 Nginx 直接提供 `public/` 中的静态文件。

生产发布采用 GitHub PR 审核、GitHub Actions 质量门禁和腾讯云 TAT 固定命令，服务器按 Git 精确 SHA 创建不可变 release 并原子切换。完整发布契约见[域名与生产发布设计](../operations/domain-deployment.md)。

该决定只适用于当前单页主站，不提前约束 M1 多页面内容站或独立项目体验的技术栈。

## 决策背景

M0 已确认的需求和约束如下：

- 公开路由只有 `/`，首版展示两个项目、技术分享状态、路线和关于信息。
- 页面没有登录、搜索、评论、订阅、表单、个性化或客户端数据状态。
- 项目体验与主站隔离；DocRestore 和 VibeCoding Project Scaffold 首版均不提供在线体验。
- 生产服务器是位于中国上海的 Ubuntu Server 24.04 LTS 轻量应用服务器，首版只承担静态文件服务。
- 站点所有者没有建站经验，需要降低本地环境、依赖升级、故障定位和恢复成本。
- 内容和公开事实必须经过 Git 审核并能追溯到仓库资料。
- 首版不使用 Cookie、访问分析、第三方嵌入或浏览器端监测脚本。

技术选型优先级依次为：可维护性、内容可信度、部署与恢复简单度、性能与可访问性、扩展能力。M0 不以框架流行度或未来假设需求作为首要依据。

## 候选方案

| 方案 | M0 适配度 | 优点 | 当前代价 | 结论 |
|---|---:|---|---|---|
| 原生 HTML + CSS | 高 | 无构建产物漂移、依赖面最小、Nginx 可直接服务、故障定位简单 | 内容与 HTML 需要同一 PR 人工同步 | 采用 |
| Astro 静态生成 | 中 | 适合后续 Markdown、多页面和组件复用 | M0 只有一个页面，需新增依赖、构建和升级责任 | 延后到触发条件出现 |
| Next.js 静态导出或服务端运行 | 低 | 路由和应用能力完整 | 对当前纯静态内容过重，运行时方案还会增加进程与安全边界 | M0 不采用 |
| Headless CMS + 前端框架 | 低 | 非 Git 用户可在线编辑 | 引入第二真相源、账号权限、API、备份和供应商依赖 | M0 不采用 |
| 手工维护的 Node.js 服务 | 低 | 可支持动态接口 | 当前没有运行时需求，会增加进程、端口、日志和攻击面 | 不采用 |

## 前端栈

### 文档与样式

- HTML：语义化 HTML5，使用 `header`、`nav`、`main`、`section`、`article` 和 `footer` 表达结构。
- CSS：单一入口 `public/styles.css`，使用 CSS Custom Properties 管理设计令牌。
- JavaScript：M0 默认不加载客户端 JavaScript。只有出现无法用原生 HTML/CSS 完成且已经写入 Spec 的交互时才增加小型本地脚本。
- 字体：使用系统字体栈，不请求 Google Fonts 或其他第三方字体服务。
- 图标：M0 没有必须依赖图标的工具栏；清晰的文本动作使用文本链接，不为少量装饰图标引入图标库。
- 动效：只允许 CSS 状态反馈，必须支持 `prefers-reduced-motion`，不使用滚动劫持、自动播放或遮挡正文的动效。

### 内容与资源

- `docs/contracts/projects.json` 是项目公开事实的机器可读真相源。
- M0 不增加站点生成器，已批准公开的项目内容由实现者同步写入 `public/index.html`。
- 质量门禁必须校验已发布项目的标识、标题、仓库链接和公开模式，防止契约与页面静默漂移。
- 项目视觉只使用经过隐私和版权检查的真实截图、界面录屏封面或工程证据，不使用通用图库图片代替项目成果。
- 图片优先使用 WebP；需要保留无损界面细节时可使用优化后的 PNG。所有内容图片必须声明 `width`、`height`、`alt`，首屏外图片使用懒加载。
- 视频未就绪时不渲染播放器或假按钮；就绪后使用本地原生 `<video>`、封面和 WebVTT 字幕。

人工同步 HTML 是当前规模下接受的成本，不是长期内容架构。当同步错误开始频繁出现或内容量达到重新选型条件时，优先引入静态生成，而不是继续扩展检查脚本模拟模板引擎。

## 工程与质量栈

| 层级 | 选择 | 责任 |
|---|---|---|
| 本地运行 | 静态 HTTP 服务 | 以 HTTP 方式预览相对路径、锚点和资源，不把直接打开文件作为正式验收 |
| 质量运行时 | Node.js 22 ESM | 执行语法、Markdown、契约、密钥和静态站点检查 |
| 包管理 | npm | 只提供统一命令入口；M0 质量脚本不依赖第三方 npm 包 |
| 版本控制 | Git + GitHub | `dev` 集成、PR 审核、`main` 生产真相源 |
| CI | GitHub Actions | 对 `dev`、PR 和 `main` 运行门禁；生产发布只接受 `main` 精确 SHA |
| UI 验收 | 真实浏览器截图 | 至少覆盖 360 x 800、768 x 1024 和 1440 x 900，检查布局、键盘和内容状态 |

### 版本与更新策略

- Node.js 固定使用 22 LTS；本地、CI 和 `package.json` engine 使用同一主版本。进入维护末期前创建升级任务并在双平台 CI 验证。
- 图表 CI 使用 Java 21 和固定 PlantUML 版本及 SHA-256；升级时重新生成图表并记录校验值来源。
- GitHub Actions 至少固定主版本并由月度维护检查 release；生产部署 workflow 落地时进一步固定到审核过的 commit SHA，升级通过 PR 和 CI 完成。
- Nginx、Git、Certbot、logrotate 和 systemd 使用 Ubuntu 24.04 官方仓库版本并接收安全更新，不混用未经记录的第三方软件源。
- 自动安全更新不能无提示重启服务器；需要重启的内核和基础组件进入维护窗口并先创建快照。
- 前端没有 npm 运行时依赖；以后新增依赖时必须提交 lockfile、启用依赖审计并记录升级责任。


首版不引入单元测试框架，因为页面没有业务逻辑。结构契约由现有 Node.js 检查覆盖；视觉和浏览器行为通过实际渲染验收。以后增加客户端逻辑时，必须同时选择对应测试层级。

## 生产栈

| 领域 | 选择 | 边界 |
|---|---|---|
| DNS | 腾讯云 DNSPod | 只管理显式记录，不使用项目泛解析 |
| Web 服务 | Ubuntu 系统包 Nginx | 静态文件、HTTPS、重定向、安全头和缓存；不运行应用代码 |
| TLS | Ubuntu 仓库 Certbot + ACME HTTP-01 | 使用 webroot 签发和 systemd timer 续期；私钥只保存在服务器 |
| 发布触发 | GitHub Actions + 最小权限 CAM | 只能调用和查询指定 TAT command |
| 服务器执行 | 腾讯云 TAT 固定命令 | 只接受 40 位提交 SHA，不接受任意脚本内容 |
| 发布目录 | SHA 不可变 release + `current` symlink | 原子切换，健康检查失败自动回滚 |
| 数据层 | 无 | M0 不保存访问者提交的数据 |

不使用 Docker、Kubernetes、PM2、运行时 Node.js、服务器面板或数据库。这些组件当前不能解决已确认需求，只会增加补丁、权限、备份和故障恢复责任。

## 兼容性与性能基线

- 支持仍在安全更新期的主流桌面和移动浏览器；核心内容在不支持增强 CSS 的浏览器中仍可阅读。
- 首次访问传输量不包含可选视频时目标不超过 1.5 MB。
- 单张项目预览图目标不超过 300 KB，并提供稳定宽高比，避免加载时布局位移。
- 首页不发起第三方运行时请求；GitHub 链接只在用户主动点击后访问。
- 生产资源使用内容类型正确的缓存策略；HTML 采用短缓存或重新验证，带版本的静态资源可使用长缓存。
- 在常见移动网络条件下，以 LCP 不高于 2.5 秒、CLS 不高于 0.1 为发布目标；自动化性能预算可在页面实现后根据真实资源固化。

## 安全与隐私影响

- 没有客户端依赖和运行时接口，降低供应链、XSS 和服务器进程攻击面。
- 所有外部链接使用完整 HTTPS URL；新窗口行为如后续引入，必须同时设置安全的 `rel` 属性。
- Nginx 使用精确主机名、只读 Web Root、安全响应头和未知 Host 拒绝策略。
- M0 不设置 Cookie，不加载分析、广告、聊天或第三方视频 iframe。
- GitHub Actions 和 TAT 凭证不进入页面、release、日志或仓库。

## 已接受的限制

- `public/index.html` 与项目契约之间存在受门禁约束的人工映射。
- 没有组件系统，重复结构在 M0 直接保留为少量 HTML；不为两个项目提前抽象模板。
- 没有自动视觉回归基线，UI 改动依赖真实浏览器截图和人工检查。
- 不支持非技术人员在浏览器中编辑内容；内容仍通过 Git PR 发布。

## 重新选型条件

出现以下任一事实时创建新的架构决策，优先评估 Astro 等静态站点生成方案：

- 已发布技术分享达到 5 篇。
- 项目详情无法在首页保持清晰扫描，需要独立详情路由。
- 同一项目或文章结构在 3 个以上页面重复，人工同步开始产生缺陷。
- 需要 Markdown/MDX、RSS、标签、站内搜索、自动站点地图或内容集合校验。
- Git PR 已成为实际内容发布瓶颈，需要评估受控 CMS。
- 引入登录、表单、评论、订阅、支付或其他用户数据处理。

框架迁移必须保留 canonical URL、稳定 slug、Git 历史、无 JavaScript 时的核心可读性和现有 Nginx 原子发布能力。

## 验收标准

- M0 实现不需要 `npm install` 即可运行质量门禁和提供静态页面。
- 浏览器加载首页时没有站点自有 JavaScript、第三方字体、分析或嵌入请求。
- `public/` 可以作为完整、可迁移的发布产物被 Nginx 直接提供。
- 项目公开事实与 `projects.json` 一致，未批准项目不出现在生产页面。
- 生产发布只来自 `main` 精确 SHA，并可在不重新构建页面的情况下切回上一 release。
- 触发重新选型条件前，不为假设需求增加框架、服务进程或数据层。
