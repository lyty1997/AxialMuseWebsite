  “同一 build 字节”固定为经过 CODE-015 路径校验的规范 POSIX 相对普通文件集合及每个文件的原始字节，不包含 mtime、uid/gid、mode 或空目录语义；符号链接、硬链接、特殊文件、隐藏路径、绝对/父级路径、控制字符、重复规范化路径与大小写冲突均在 build、release 和上传前失败。封装器在复制前后重算按路径排序的 SHA-256 树摘要，`release.json` 保存 `sourceBuildTreeSha256`，并证明 `payload/` 相对路径与字节一一对应；期间任何新增、删除、改名或字节变化失败。服务器安装时统一目录 `0755`、普通文件 `0644` 并按内部清单复核，因此 GitHub 外层归档的权限归一化不参与内容身份。

  最终 Action 只上传一次精确 `dist/release/`，禁止 glob、多路径、同名合并和 `overwrite: true`，使用 `if-no-files-found: error` 并显式排除隐藏文件；上传前门禁必须已经证明 release 中不存在隐藏路径。该 job 不配置 `actions/setup-node` cache、不调用 cache restore/save Action，也不读取跨 step、跨 job 或跨 run 共享/复用的依赖或 build cache；E-010 为本次 job 创建且不复用的私有 npm cache 仍是必需隔离目录。独立 release 校验通过后，仓库内受控 `check:artifact` 入口复用冻结依赖中的 production checker，并以零新增 npm 依赖的文件树核心对 `dist/release/` 全文件树计算一次不写入 artifact 的 `releaseContentSha256`，随后不插入其他命令而执行上传；它与上传 Action 返回的外层 `artifactDigest` 分别映射为 job outputs。前者是服务器必须从下载并解包后的 exact release tree 独立重算的上传前期望值，不能从 artifact 内的自报 metadata 回填；后者绑定 GitHub 保存的外层 artifact。展示名称固定为 `axial-muse-site-<sha>-<run-id>-<run-attempt>`，真正身份是不可变 artifact ID、上述两个摘要、canonical repository、workflow run ID/attempt 与 `GITHUB_SHA`。`deploy-production` 只能直接消费这些输出，禁止按名称、pattern、latest、任意 URL 或跨 run 搜索，也不能部署中间质量输出。Action 的精确版本和 commit SHA 仍须通过 D-077 准入；upload Action 的固定源码与 `action.yml` 只需证明 artifact ID/digest 输出及不可变/overwrite 语义，摘要比较属于 deploy/服务器职责，不要求上传 Action 证明不存在的 download mismatch 行为。官方 upload action 说明 artifact ID/digest、不可变性、覆盖会换 ID、隐藏文件与权限边界：[actions/upload-artifact](https://github.com/actions/upload-artifact)。

  prerequisite jobs 与 `production-artifact` 的 `GITHUB_TOKEN` 权限固定为仅 `contents: read`，`deploy-production` 为读取 canonical ref 和当前 run artifact 元数据仅可使用 `contents: read` 与 `actions: read`；所有未列权限均为 `none`，禁止任何 write、`id-token: write` 或 attestation scope，也禁止 repository/environment Secret 进入 producer。`deploy-production` 在引用 CAM Secret 或调用腾讯云 API 前，必须用只读 GitHub API 重新验证当前 canonical `refs/heads/main` 仍精确等于本次 commit SHA，并复核 repository、run、artifact ID、`head_sha`、未过期状态与外层 digest。upload job/TAT 的 `artifactDigest` 固定为裸 64 位小写 hex，REST metadata 必须逐字节等于 `sha256:` 拼接该值；缺失或其他算法、大小写、长度和前缀形式全部失败，不做宽松归一化。不相等就结束，不上传、重建、回退或继续调用 TAT。concurrency 只提供生产互斥，不提供等待顺序或 main 新鲜度保证，不能替代此检查；发布历史 SHA 必须进入另行授权的恢复流程，普通 `workflow_dispatch` 重跑没有该权限。依据见 GitHub 的 [workflow/job permissions](https://docs.github.com/en/actions/writing-workflows/workflow-syntax-for-github-actions#permissions) 与 [concurrency 语义](https://docs.github.com/en/actions/writing-workflows/choosing-what-your-workflow-does/control-the-concurrency-of-workflows-and-jobs)。

  fixture 与 workflow 静态检查必须覆盖：任一 prerequisite 非成功、PR/fork/Dependabot/`dev`、错误 dispatch ref、matrix producer、`always()`/`continue-on-error`、缓存与浮动 Action；预存/空/preview build、浅历史、SHA 或 manifest/lock 漂移；封装期间字节变化、upload 前整版替换及非法路径；多次上传、错误目录、`overwrite`、非法 ID/digest；过宽权限、旧 run、main 移动，以及错误或过期 artifact。producer 任一失败不得生成最终 artifact 或调度 deploy；deploy 身份或 main 新鲜度失败必须在读取 CAM Secret 前停止。本决定只保证最终 build 自身完整重验，不宣称跨 runner 可复现构建，也不引入 artifact attestation。#33/#35/#14 已形成确定性封装、服务器 verifier 和 producer/upload 本地实现，但 canonical `main` 真实 artifact 与 Issue 证据仍待。#36 已完成服务器盘点、SSH、OS UFW 与软件事务；D-125 历史回执仍为 `environmental_inconclusive`。D-126 唯一一次只读探针已以 `status=complete oracleMatch=true` 关闭当前内容关系缺口，未写服务器且授权已消费；它不证明历史因果或授权 transition。重启后验和 verifier 安装继续为 GAP。

- **E-016 / 2026-07-23 — 单一内容装配与零公开文档适配**：#26 的 production 构建只允许一个以根级 `site-content/` 为物理根、`routeBasePath: "/"` 的 docs 实例，current-only 选项精确为 `includeCurrentVersion: true`、`onlyIncludeVersions: ["current"]`、`tags: false`。不得使用 `disableVersioning: true`：Docusaurus 3.10.2 在没有版本清单的当前内容站点会拒绝该选项，它不能代表 current-only。构建层每次完整扫描 projects/authors/topics/project-experiences 四份领域注册表、`static-public-assets.json` 和内容根后，必须把同一次 `validateProjectCatalog` 成功返回的原对象依次交给文章校验、导航、静态素材计划与框架投影；文章成功批次同样携带只在领域层可验证的 provenance。任何失败都不得返回合法子集、复用上次成功结果或退回框架默认推断。扫描器必须完整拒绝未知分区、非法 Markdown/MDX 布局、category metadata、version roots、localized 第二内容根、符号链接、特殊文件、大小写和 realpath 漂移；首轮读取结束后还要重验全部目录成员、文件身份与完整字节，Docusaurus 每次解析前后再与该批路径和字节快照核对。内容批次摘要与同次静态计划的模式、全部 allowed/excluded 条目语义、字节长度和 SHA-256 以域分隔 framing 合成唯一不公开输入摘要，共同绑定 build、独立 checker 与切换后终态 checker。这使 include、解析回调、二次 MDX 读取、跨阶段正文漂移，以及计划外未发布素材在 build/check 之间换字节都不能绕过同一输入闭包。

  当前真实内容只有两个 `planned` 项目正文而没有 production 公开 doc。已锁定的 Docusaurus 3.10.2 在该输入上先得到 `docs=[]`、`drafts=[2]`，随后官方 docs 插件的 `contentLoaded` 访问 `docs[0].id` 并崩溃；官方配置不存在既保持实例启用、又不生成占位或隐藏路由的零公开文档模式。为不改变项目状态、依赖图或公开路由，本站采用精确版本绑定的窄适配：本地 classic-derived preset 从已准入 `@docusaurus/preset-classic` 返回值中识别唯一官方 docs 插件配置，使用已准入 `@docusaurus/utils` 的模块加载能力取得该精确实现，保留其 `validateOptions`、`loadContent`、MDX loader、sidebar、route 和其余生命周期，只包装 `contentLoaded`。适配器先验证 current-only、unversioned 的 `loadedVersions/docs/drafts` 精确结构和与已验证内容的一一对应；只有 production 的公开 `docs` 精确为空时才不调用官方 `contentLoaded`，从而不生成 docs route、catch-all 或伪造 global data。有公开 doc 时，官方实现会把同版本 `drafts` 序列化为浏览器 `draftIds`；production 因此只浅克隆 `args -> content -> loadedVersions -> current version`，仅把克隆版本的 `drafts` 替换为新空数组后委托，并保留公开 `docs` 数组及成员、actions、其余 version 字段和 lifecycle `this` 的原身份。委托前后必须证明原参数对象图 descriptors 不变、受控投影不变且内容仍属当前批次，官方异常也要在该复验后原样重抛；preview 仍原样委托。版本、preset 输出、插件路径、生命周期或内容结构漂移全部失败，不能条件关闭 docs、建立第二实例、写占位 Markdown、使用 `unlisted`、等待某个项目提前公开或直接导入未声明的传递包。

  配置加载与插件初始化分责：根配置只读取并重验受控 build context，不扫描内容、不创建 content session，且可重复加载；本地 preset 在取得并改写 classic 返回的唯一官方 docs 配置前，为每次真实插件初始化完整创建一个只服务本构建的 eager session。docs 适配器、sidebar 生成器和 `createContentDataPlugin` 都由同一个已冻结 session 对象及其内嵌 adapter session 驱动，不通过惰性 Promise 重复装配，也不形成跨构建缓存。`src/build/content/index.ts` 的构建层公共 API 只导出 `loadValidatedContent`、`createParseFrontMatter`、`createSidebarItemsGenerator` 与 `createContentDataPlugin`；session 在官方 docs 构造器读取 markdown 配置前安装 `createParseFrontMatter`，并把同一导航模型交给稳定名称 `projectsSidebar`、`writingSidebar` 的 sidebar 生成器，以及只包含 `projectNavigation`、`writingNavigation` 的安全 global data。Docusaurus 的 `createData` 发生在 browser bundle 之前，单凭“不消费返回路径”不能证明私有索引未被打包；因此日期索引在 bundle 已完成的本地插件 `postBuild` 中才以原子普通文件写入本次 `generatedFilesDir/axial-muse/article-date-index.json`，独立 checker 再按同一投影逐字节核对。该 `postBuild` 只生成私有文件和输入摘要，不承担最终通过判定；索引不得进入 global data、route、static、最终 `build/` 或浏览器 bundle。production 公开文章的规范分类项目、相关项目和相关文章都必须已经公开，公开项目的 `relatedWriting` 也只能指向公开文章；draft、planned 等未发布源仍可引用已经登记且通过自身 schema 的目标。该闭包不能通过泄露未发布显示名、静默隐藏关系、移动到“通用技术”或重复身份绕过。空导航组省略；preview draft 缺 `updatedAt` 时排在有日期 draft 之后。#8 仍独占真正的 `build --dev`、全站 noindex、无 sitemap 和候选激活。

  Docusaurus 3.10.2 并行执行所有插件 `postBuild`，官方 sitemap 也在该阶段写文件，而 broken-link 检查发生在全部 `postBuild` 之后。因此 #26 的最终 route、canonical、sitemap、侧栏、私有日期索引和 E-008 素材泄漏验收不得放在本地 `postBuild`。受控 `scripts/build/build-site.mjs` 必须先取得 owner 绑定的仓库级独占构建锁，在改变候选或既有 `build/` 前回收上次固定 retired/quarantine；回收失败时现有 `build/` 保持不变。内建 `build` 子进程随后对未发布的 `.axial-muse-build-candidate-<owner>` 完整构建并写入同 owner 的私有输入摘要，再由独立 `axial-muse:check-production` external command 创建全新 session，重新扫描、核对输入摘要并串行验证候选；检查进程不继承前一进程的内存或成功状态。

  首次 checker 成功后，入口在锁内把既有 `build/` 暂存为完整 backup、把候选改名为 `build/`，再对已经位于最终路径的树运行第二次 fresh checker，关闭检查到切换之间的 TOCTOU。两次 directory rename 是受独占锁保护且可回滚的事务切换，不宣称为 POSIX 单 syscall 目录交换。终态检查成功后，旧 backup 只通过同文件系统 rename 进入唯一固定 retired 路径，输入摘要被删除，最后成功释放锁作为 commit point；commit point 后不得再执行可能改变结果的操作。retired 是完整上一版或失败候选的私有隔离，不是可发布候选，并在下一次取得锁后、任何新变更前回收，因此递归删除失败只会阻止下一次构建而不会制造“命令失败但新 build 已激活”。commit point 前任一构建、断链、检查、摘要、rename、清理或锁释放失败，都必须把调用前 `build/`（或原先不存在的状态）恢复后非零退出，并把本次候选移出可误用名称；该流程不生成 E-015/#33 的 release 身份、摘要或封装。
