# 内容发布流程

状态：active
最近更新：2026-07-16
适用范围：M0-M2 项目、技术分享和页面文案的创建、审核、上线与修订

## 目的

本文定义内容从想法到生产发布的可追溯流程。目标不是提高发布数量，而是保证每项公开内容有来源、有状态、能修订，并与站点代码通过同一 Git 工作流发布。

## 内容真相源

### 已确认的目标流程

内容由 Git 仓库管理并通过 Docusaurus 静态构建发布。仓库中的内容文件、页面组件和经过确认的结构化契约是可编辑真相源；Docusaurus 构建产物是可重复生成的发布结果，不作为人工编辑入口。生产服务器只接收并提供静态产物，不在服务器上编辑正文，也不运行 Docusaurus 或 Node.js 服务。

项目介绍与技术文章由单一 docs 内容实例构建，但分别进入项目侧栏和技术分享侧栏。单一实例不改变两类内容各自的领域字段和审核规则；首版不启用 blog，也不因 Docusaurus 的可选能力自动生成时间流、归档、Feed、作者页、主题页或其他未批准路由。两套侧栏的最终内容必须与已确认的内容真相源和规范归属一致；采用自动生成还是受校验的显式配置，以及具体排序方式，均由后续决策确定。

D-055 确认技术文章的领域内容模型与其引用的 Git 注册表是唯一可编辑真相源。Docusaurus 所需元数据只能在构建期只读直传或派生，不回写源内容，也不把派生的框架字段提交为第二份事实。该方向同样约束未来确认的项目内容来源，但当前不决定 `projects.json` 与项目 Markdown/MDX 的长期关系。

D-058 确认技术文章直接在源 frontmatter 顶层填写 Docusaurus 原生根相对完整 `slug`，例如 `/writing/dependency-inversion`。单一 docs 实例使用 `routeBasePath: '/'`，默认 frontmatter 解析结果中的 `slug` 原样参与路由；发布流程不再维护短文章 slug 或构建期栏目路径派生值。项目注册表短标识与项目介绍内容来源不受本决定改变。

D-056 曾确认使用全局 `markdown.parseFrontMatter` 与本地纯投影函数，D-057 曾确认通过未来内容根内的 `writing/` 子树分流该适配。两项决定形成前没有先完成 Docusaurus docs 原生字段的逐项能力核对。用户确认 D-058 后要求回退受影响部分，因此 D-056、D-057 当前只保留历史方案，实施授权暂停；重新决策前不创建解析钩子、投影函数、类型目录、成员清单或 `contentType` 字段。

普通技术文章默认使用 Markdown。只有确实需要文章专属组件、且普通 Markdown 无法满足时才使用 MDX；MDX 只能引用仓库内经过审核的 React 组件。Docusaurus 默认通过 MDX 管线处理两类文件，这里的区分是编辑和审核边界；是否启用其他解析模式仍待后续技术设计。Docusaurus docs 内容根物理路径、内部组织、原生字段 fit-gap、最小适配范围和组件审核机制属于后续未决项，在这些规则完成前不创建 MDX 文章。

技术文章已通过 D-036 选择完整编辑模型，能力范围覆盖核心发布信息、作者、项目与模块组织、主题标签、系列关系、SEO 覆盖、推荐控制和公开修订记录。D-037 进一步确认元数据与正文保存在同一个 Markdown 或 MDX 文件中，少量核心字段位于 frontmatter 顶层，复杂且可选的元数据按职责嵌套分组，不使用文章级 sidecar 文件。D-038 至 D-050 已确认核心字段、受控 SEO 描述覆盖、显式日期、作者注册表、“项目-模块-主题标签”的组织基数及 `classification` 唯一分组；其中 D-035、D-038 的文章字段值与映射语义已被 D-058 部分替代。各注册表、其余字段与 Docusaurus 原生能力关系仍需逐项决定。

`authors` 引用 Git 管理的单一 JSON 对象，作者 ID 是对象键。首版作者记录包含必填 `displayName` 和嵌套的 `links.github`；`lyty1997` 的初始显示名同为 `lyty1997`，GitHub 地址为 `https://github.com/lyty1997`。首版不加入简介、头像或其他社交链接。个人作者、Axial Muse 站点品牌、未来发布组织和未来中央账户互不替代；是否提供作者详情页由后续信息架构决策决定。

`summary` 是目录摘要、正文导语、默认 meta description 和默认分享描述的单一来源。只有普通摘要无法满足时才填写 `seo.description` 或 `seo.socialDescription`；后者按自身、`seo.description`、`summary` 的顺序回退。禁止新增 `excerpt`、从正文自动截取、在页面组件硬编码第二份摘要，或提交空白及与回退值完全相同的冗余覆盖。新增覆盖必须在评审中说明原因，正文、标题或摘要发生实质修改时必须复核已有覆盖。

`publishedAt` 与 `updatedAt` 使用 `YYYY-MM-DD`。`draft` 不得填写 `publishedAt`，可选 `updatedAt` 且不公开；`published` 和 `archived` 必须同时填写，首次发布时两个日期相同，之后 `publishedAt` 保持不变。发布辅助命令按 `Asia/Shanghai` 在作者操作阶段写入源文件，修改随正文进入 Git diff；CI、Docusaurus 和生产服务器只读校验，不在构建或部署时注入时间。公开文章跨日期发生可见修改时必须更新 `updatedAt`，迁移旧文章可在提交前手工填写真实历史日期。

技术文章不使用通用主分类。组织字段只存放在必填的 `classification` 对象中：`classification.project` 和 `classification.module` 均可为空且各最多一个；`classification.module` 只能与 `classification.project` 同时存在，并必须引用该项目所属模块。只有项目的文章进入项目根级，两者均为空的文章进入独立通用分组。`classification.topics` 必填 1-5 个受控主题 ID。跨项目文章只选择一个主项目，其他项目关系不得使文章在多个项目侧栏重复出现。项目、模块和主题的稳定 ID 引用 Git 注册表，显示名称与 ID 分离；这些关系不进入 URL，重分类也不修改 URL。

构建门禁必须拒绝缺少 `classification`、孤立模块、模块与项目归属不一致、主题为空、主题超过 5 个、未登记 ID，以及同一文章被配置到多个规范目录位置；还必须拒绝在 frontmatter 顶层或 `relations`、`taxonomy` 等其他分组中重复定义项目、模块或主题组织字段。注册表结构与路径、通用分组公开名称和跨项目相关关系字段尚未由用户决定，因此当前只固化分组语义与校验责任，不创建 schema 或注册表文件。

### MDX 使用门禁

每次新增或修改 MDX 文章时，评审必须明确：

- 为什么普通 Markdown 无法满足该文章。
- 引用了哪些仓库内组件，以及这些组件的审核记录。
- 组件是构建时静态输出还是需要浏览器端交互。
- 是否新增浏览器 JavaScript、外部请求、用户数据或第三方依赖。
- 组件失败时是否仍能阅读文章的核心内容。

允许使用 MDX 不代表批准任意 UI 框架、远程模块、第三方脚本或客户端加载策略。对应需要出现时，必须先完成独立决策。

### 迁移前的当前状态

当前仓库尚未引入 Docusaurus。`docs/contracts/projects.json` 当前仍保存项目标题、状态、日期、仓库和展示状态等公开事实，是项目条目的机器可读来源；`public/index.html` 是迁移前的手写发布结果。人工同步 contract、HTML 与未来项目正文不作为长期方案；迁移后是否继续以 `projects.json` 作为项目领域来源，仍需用户决定。

在 Docusaurus 原生字段 fit-gap、必要的最小适配、内容根及内部目录契约、侧栏生成和迁移方案确认并完成迁移前，现有页面修改仍需同步 contract、HTML 和站点门禁，避免当前公开结果继续漂移。迁移完成后，页面必须由已确认的内容模型生成，停止人工同步同一份项目或文章正文。

当前不新建独立 CMS、数据库或在线表格作为第二真相源。未来只有 Git 审核流程被事实证明不适用，并经过新的用户决策后，才评估 CMS。

迁移必须保留 Git 历史、发布日期和旧 URL 语义。技术文章 `slug` 由作者按 D-058 直接填写为 Docusaurus 原生根相对完整路径，是公开 URL 的唯一真相源；不得从文件名、目录、标题、日期、分类或系列生成，也不得再生成第二个框架路由字段。构建时必须校验格式和全站路由唯一性。发布后如需修改，必须在同一变更中增加旧 URL 永久重定向并更新 canonical URL 与站点地图。当前已确认部分字段、组织语义和原生文章 slug；内容类型判据已经重新开放评审，完整 schema、注册表、内容根物理路径和内部组织仍未完成决策，因此当前不创建文章文件。

目标架构和当前待决策边界见[主站目标架构](../architecture/main-site-target-architecture.md)。

## 内容状态

> D-040 确认下表为技术文章 `publicationStatus` 的完整枚举。项目发布状态和项目体验状态属于独立模型，不受本表改变。

| 状态 | 含义 | 是否公开 |
|---|---|---|
| `draft` | 正在写作，事实与结构尚未完成审核 | 否 |
| `published` | 已通过审核并进入生产站点 | 是 |
| `archived` | 不再维护但保留历史价值 | 是，并明确归档状态 |

生产构建不得为 `draft` 生成列表项、正文路由或 sitemap 条目。`planned` 只作为 Issue、路线或选题记录，不进入文章集合，也不占用文章 slug 或 URL。`archived` 正文保持公开，并明确标注不再维护。

## 选题与优先级

首版内容围绕真实项目产生，按以下顺序排序：

1. 能解释一个已遇到的问题和真实约束。
2. 有可展示的设计、代码、实验或复盘证据。
3. 对后续项目决策或读者实践有复用价值。
4. 能与现有项目或系列形成清晰关系。

只有观点、没有验证材料的内容可以发布，但必须明确标注为观点，并说明推理范围。涉及外部事实时优先链接官方文档、标准、论文或原始公告。

## 内容模板

### 技术分享

1. 标题与摘要。
2. 问题背景：为什么需要解决。
3. 约束与非目标：本次没有解决什么。
4. 方案选择：考虑过哪些路径，为什么选择当前方案。
5. 实现或实验：给出可复核步骤和必要代码。
6. 验证结果：说明通过、失败和没有覆盖的部分。
7. 复盘：哪些结论可复用，哪些只适用于当前项目。
8. 参考来源与更新时间。

### 项目详情

1. 项目摘要与当前状态。
2. 目标用户或使用者。
3. 核心问题与边界。
4. 架构和关键决策。
5. 当前成果与证据链接。
6. 已知限制与风险。
7. 相关技术分享。
8. 最近更新时间与下一阶段。

## 发布工作流

1. **建立记录**：为选题创建 Issue 或路线条目，写明目标读者、问题、证据来源和内容状态。
2. **起草**：在功能分支修改内容；事实、观点、计划和未知信息使用不同表达。
3. **自检**：检查真实姓名、联系方式、截图、日志、路径和示例数据，移除密钥与隐私信息。
4. **本地验证**：运行 `npm run quality`，启动本地预览并检查桌面端、平板端、移动端、链接和资源。
5. **创建 PR**：说明设计文档依据、公开内容变化、来源、截图和验证结果。
6. **预览审核**：使用分支预览确认排版、导航、SEO 元数据、图片和索引策略。
7. **内容审核**：逐项核对标题、摘要、事实来源、状态、日期、版权和承诺边界。
8. **发布**：变更先提交并推送到 `dev`；集成验收通过后创建 `dev -> main` PR，required checks 通过再合并，由生产部署自动上线。禁止直接 push `main`。
9. **上线核验**：检查生产 URL、canonical、分享卡片、关键链接和实际部署提交。
10. **记录**：在 [项目进度](../progress.md) 记录发布时间、提交、URL、验证和遗留问题。

任何一步失败都保留真实错误并修复根因，不通过跳过门禁或手工覆盖生产文件完成发布。

## 审核清单

### 可信度

- 标题和摘要与正文结论一致。
- “已完成”“已验证”“可用”等表述有对应证据。
- 推测、个人观点和未来计划没有写成客观事实。
- 外部引用链接到原始出处，引用范围符合版权要求。

### 隐私与安全

- 截图已检查浏览器标签、用户名、主机名、路径、邮箱、通知和后台标识。
- 示例凭证为明显无效占位符，不接近真实密钥格式。
- 不公开客户、内部沟通、未授权数据或未公开商业计划。
- 外部嵌入、分析脚本和表单没有随内容修改被悄然引入。

### 可维护性

- slug、标题、摘要、发布状态和日期符合已确认的内容模型。
- `classification.project`、`classification.module` 和 `classification.topics` 中的 ID 均能在对应注册表中解析。
- `classification.module` 只在 `classification.project` 存在时填写，并且隶属所选项目。
- `classification.topics` 存在且包含 1-5 个主题 ID。
- 每篇文章只生成一个规范目录条目，跨项目相关关系不产生重复侧栏入口。
- 图片有来源、替代文本和合理尺寸。
- 内部链接使用站点约定路径，没有链接到本地文件或预览域名。
- 发布日期和更新时间含义正确，不用小修改伪装成新发布。

## 图片与附件

- 优先使用本人项目的真实截图、架构图和必要的演示素材。
- 第三方图片必须有明确授权或符合许可，仓库记录来源和许可信息。
- 发布前移除 EXIF 等不必要元数据，压缩到满足清晰度的最小尺寸。
- 图片文件名使用可读的 ASCII slug；同一内容的多尺寸版本保持一致命名。
- 不上传包含真实凭证、私人账号、未公开域名或内部网络信息的素材。

## 修订、纠错与归档

小型文字修正直接更新 `updatedAt`；影响结论、步骤或安全性的修改，在正文增加简短修订说明。发现高风险错误时先从导航和列表移除或添加醒目标记，再完成修复，不让错误内容继续作为当前建议传播。

项目、模块或主题关系发生变化时，只更新组织引用和必要的 `updatedAt`；不得改写或重新生成 slug、canonical URL 或公开 URL，也不得为同一文章新增第二个规范目录入口。

内容不再适用但仍有历史价值时转为 `archived`，说明原因和替代内容。除隐私、版权、安全或法律原因外，不直接删除已被外部引用的 URL；使用归档页或永久重定向保存链接语义。

## 发布节奏

M0 以完成 2 个可信项目条目、真实视觉证据和不虚构文章的技术分享空状态为上线内容基线。完整技术分享采用“完成即发布、每月复盘”的增量节奏，不阻塞主站首次上线，也不设置为了数量而发布的硬指标。月度复盘检查内容状态、失效链接、过时结论和下一批选题。

## 验收标准

- 每项公开内容有状态、更新时间、负责人和可追溯提交。
- 技术分享包含问题、约束、取舍、验证和来源。
- 发布只能由 Git 合并触发，生产内容与 `main` 一致。
- 上线前完成质量、渲染、隐私、版权与链接检查。
- 修订和归档不会破坏已有 URL 或隐藏重要历史变化。
