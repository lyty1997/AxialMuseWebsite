# 内容发布流程

状态：active
最近更新：2026-07-27
适用范围：M0-M2 项目、技术分享和页面文案的创建、审核、上线与修订

## 目的

本文定义内容从想法到生产发布的可追溯流程。目标不是提高发布数量，而是保证每项公开内容有来源、有状态、能修订，并与站点代码通过同一 Git 工作流发布。

## 内容真相源

### 已确认的目标流程

内容由 Git 仓库管理并通过 Docusaurus 静态构建发布。仓库中的内容文件、页面组件和经过确认的结构化契约是可编辑真相源；Docusaurus 构建产物是可重复生成的发布结果，不作为人工编辑入口。生产服务器只接收并提供静态产物，不在服务器上编辑正文，也不运行 Docusaurus 或 Node.js 服务。

项目介绍与技术文章由单一 docs 内容实例构建，但分别进入项目侧栏和技术分享侧栏。两套侧栏均由官方 `sidebarItemsGenerator` 从已校验内容、注册表和当前 `docs[].id` 只读生成，不提交第二份成员清单。项目按 `navigationOrder` 排序；文章先显示“通用技术”，随后按项目、模块和文章日期排序。首版不启用 blog，也不生成时间流、归档、Feed、作者页或主题页。

D-055 确认技术文章领域模型与其 Git 注册表是唯一可编辑真相源。E-001 对项目采用职责拆分：`projects.json` 拥有结构化事实，`site-content/projects/<project-id>/index.md|index.mdx` 只拥有长文正文；构建期从注册表只读派生项目 title、description、完整路径和草稿行为，不回写或双写。

D-058 确认技术文章直接在源 frontmatter 顶层填写 Docusaurus 原生根相对完整 `slug`，例如 `/writing/dependency-inversion`。单一 docs 实例使用 `routeBasePath: '/'`，默认 frontmatter 解析结果中的 `slug` 原样参与路由；发布流程不再维护短文章 slug 或构建期栏目路径派生值。项目注册表短标识与项目介绍内容来源不受本决定改变。

D-056 曾确认使用全局 `markdown.parseFrontMatter` 与本地纯投影函数，D-057 曾确认通过未来内容根内的 `writing/` 子树分流该适配。两项决定形成前没有先完成 Docusaurus docs 原生字段的逐项能力核对，因此在 D-058 后重新开放评审。D-059 已以更小职责重新确认 D-056：调用默认解析器后，`title` 与完整 `slug` 原样使用；构建内存中的 `description` 始终由源 `summary` 派生，只有 `publicationStatus: draft` 派生 `draft: true`。作者不得在源 frontmatter 中另写 `description` 或 `draft`。D-060 随后把 `writing/` 子树重新确认为独立的唯一技术文章类型边界，不再把目录判型本身绑定到 D-056。

`seo.description` 与 `seo.socialDescription` 不映射到原生 `description`；页面 `<head>` 继续使用 D-046 已确认的两条回退链，只有元数据组件、标签合并、避免重复标签和契约测试的实现仍待后续主题与 SEO 契约确定。`authors`、`publishedAt`、`updatedAt` 与 `classification` 不映射为 `last_update`、`tags` 或 blog 字段，也不启用 `unlisted`。

单一 docs 内容根已由 D-061 固定为仓库根 `site-content/`。规范化后位于 `site-content/writing/` 子树内的 Markdown/MDX 都是技术文章候选，并且必须先通过技术文章 schema 再执行 D-059 投影；失败时中止构建，不得退回普通 doc。边界外只确定为非技术文章，不自动成为项目内容，也不运行文章投影。不得增加 `contentType`、独立成员清单，或用字段存在性、`slug`/URL 前缀、侧栏成员等建立第二判据。目录不生成或覆盖文章 URL、完整 `slug`、分类、侧栏归属或排序。

D-062 进一步确认每篇文章使用 `site-content/writing/<source-name>/` 独立源码目录，并且该目录恰好包含 `index.md` 或 `index.mdx` 之一作为唯一正文入口。根级 Markdown/MDX、非 `index` 正文、同目录双入口和额外 Markdown/MDX 都必须失败。`<source-name>` 只用于稳定仓库组织，不生成或校验 slug、分类、doc ID 或侧栏。D-064 已固定当前 doc ID 只作为框架内部引用，正文使用带扩展名的源码相对链接，侧栏消费插件提供的当前 `docs[].id`。

D-063 将 `<source-name>` 进一步固定为作者手工确定的稳定可读语义源码名：长度为 1-64 个 ASCII 字符，完整匹配 `^[a-z0-9]+(?:-[a-z0-9]+)*$`，并在当前 `site-content/writing/` 文章直接子目录命名空间内全局唯一。作者可以独立选择与 slug 尾段相同的文本，但工具不得从标题、slug、分类、日期或正文自动生成、同步或静默纠正目录名，也不得用目录名生成或校验 URL、canonical、分类、侧栏或排序。首次发布前的受控改名必须原子移动完整目录、保持目录名与 slug 变更相互独立、更新全部路径和 doc ID 消费者，并通过完整构建及断链检查；首次发布后只有拼写错误或持续造成严重歧义时，才可经用户对该次迁移明确授权后改名，且公开 slug 与 canonical 必须保持不变。默认 doc ID 会随父目录改名；D-064 后续确认了框架内部 doc ID、文章间链接与侧栏身份引用策略。

D-064 为每篇技术文章增加必填顶层 `articleId`。该值是全站唯一、终身不可修改或复用的 UUIDv7 领域身份，自文章创建起与唯一正文入口一起进入 Git；标题、正文、源码目录、slug、分类、发布状态和日期变化都不修改它。articleId 不进入 URL，不映射为 Docusaurus 原生 `id`，也不生成或校验源码目录、slug、canonical、分类或侧栏。UUIDv7 时间字段只记录生成器在分配 ID 时采用的 Unix 毫秒时间源值，可用于 UUID 值的技术排序与未来存储索引局部性，但不保证真实业务事件顺序；不得将其当作 `createdAt`、`publishedAt` 或 `updatedAt`，也不得用于补写日期、公开排序、SEO、sitemap、列表、侧栏、归档或日期搜索。D-065 后续确认了生成责任和作者入口，D-066 又确认 Node 24 LTS 原生生成后端及非严格递增语义；E-013 固定统一结构化解码、HEAD 可达完整历史、lineage 父状态、浅仓库/partial object store 失败和删除后重引规则，具体命令与测试见编码 Spec。

D-065 将新文章的正常创建方式固定为作者显式运行仓库内 Node.js 文章创建命令。作者先显式确定符合 D-063 的 `<source-name>`；命令在同一次创建操作中建立尚不存在的文章目录、D-062 的唯一正文入口，并把新生成的 UUIDv7 作为顶层 articleId 写入一次。成功必须同时产生三者，失败必须恢复到调用前状态，不得留下目标文章目录、正文入口或本次创建产生的其他持久化结果；普通创建命令不得覆盖既有目录，也不得为既有文章覆盖、修复、轮换或补写 articleId。命令不得从 articleId、标题、slug、分类、日期、正文或其他字段相互推导、同步改写或静默纠正领域值；旧文分配使用独立迁移流程。

创建命令只写入获准运行本站 Node.js 的 Linux 作者工作区，作者必须先审查 Git diff。命令不自动暂存、提交、推送或发布。Git hook、PR bot、CI、Docusaurus、预览、发布自动化和生产服务器均不得隐式触发创建命令或生成、修复 articleId；缺失、非法、重复或发生未授权修改时只能让只读门禁失败并定位源文件。命令名、参数、Markdown 模板、作者锁与 staging 原子目录、UUID 文本与历史检查、错误契约和测试由编码 Spec 固定；创建前必须通过 E-013 的同一历史实现验证工作区候选，浅克隆、缺失对象或历史冲突时不写 staging。M0 不提供 MDX 创建参数。#24 已实现上述直接 Node 入口、完整历史接线与原子事务，并依 D-103 获准纳入当前专题分支提交及同名临时 ref；远端验证仍待取得，且真实主题注册表仍为空，因此本轮不把临时 fixture 成功表述为已有真实文章可创建。

D-066 将未来获准执行本站命令的作者工作区、仓库质量门禁、CI 和 Docusaurus 静态构建统一到 Node 24 LTS 主版本，最低 24.16.0，允许范围为 `>=24.16.0 <25`。文章创建命令使用 `node:crypto.randomUUIDv7()`，不得引入 `uuid` 或其他 UUID npm 包、系统 CLI 或在线生成服务。原生 API 的时钟非单调，本站不要求同毫秒、时钟回退、跨进程或跨机器严格递增，也不增加计数器、共享状态、重试到大于前值或时间修正包装；当前树和 Git 历史的唯一性由 E-013 独立门禁。仓库现已建立 Node 24 版本文件和 E-010 双端点隔离校验；D-080 已让本地 pre-commit 子进程从 `.nvmrc` 选择精确 Node 24，同时系统与新 Bash 会话默认仍解析 `/usr/bin/node` `v22.22.0`。D-097 至 D-099 已把 Ubuntu workflow 迁移到 Node 24 主/最低端点，并接入完整 checkout、内容历史门禁与静态供应链证据，再依 D-100 纳入专题分支；普通 CI 不再运行 live audit。该分支已本地验收，D-101 仅授权交付到不触发现有 `main`/`dev` workflow 的同名临时 ref，因此远端运行证据仍待后续集成验收。生产 Nginx 只接收并提供静态制品，不运行作者命令或 Node.js 请求服务。

D-067 将仓库根 `.nvmrc` 固定为正常作者、质量和构建的唯一精确 Node 版本源，初始值只记录在决策日志；`engines.node` 继续表达 D-066 的兼容范围。Linux 作者通过 nvm 读取该文件，文章创建命令必须先断言实际 Node 等于 `.nvmrc`。Ubuntu CI 的最低版本入口只以 `engines` 下界替换正常入口的精确版本断言，再调用同一共享检查与构建负载；它不得调用文章创建命令、生成发布制品或进入发布链，也不得通过通用跳过开关削弱正常入口。安全 patch 及时走独立 PR，其他 patch 每月检查；PR 先提出 `.nvmrc` 候选值，Ubuntu CI 的主基线、最低端点、PlantUML 和发布必需门禁通过后才可合并，不能自动合并。当前仓库已经创建 `.nvmrc` 和兼容 `engines.node`，E-010 runner 会失败关闭校验主/最低 Node 与各自随附 npm；D-097 已在工作区接线并本地验收目标 Ubuntu CI 双端点，#24 作者工具也已把正常作者入口收紧为 `.nvmrc` 精确 Linux 主端点，并依 D-103 获准纳入当前专题分支提交及同名临时 ref，远端结论仍待验证。

D-072 已将执行平台收敛到 Linux 作者环境和 Ubuntu-only CI。内容发布流程不再维护第二套 Node.js、质量检查或 Docusaurus 构建路径。

唯一正文入口同时保存 articleId、当前完整 slug、发布状态、`publishedAt` 与 `updatedAt`，是这些字段与正文之间的唯一可编辑绑定。schema 通过后，构建在临时目录只读派生按 articleId 排序的 JSON 索引；每条记录仅包含 articleId、slug、publishedAt 与 updatedAt。该索引从当前源内容重建，不回写、不手工编辑、不提交，也不复制到公开 `build/`；生产构建完全排除 draft。它只供构建期路由、历史身份和重定向检查消费，不建立运行时缓存。本规则不批准站内搜索、日期筛选 UI、搜索插件、外部搜索服务或查询数据采集。

Docusaurus 内部不把 articleId 当作框架 ID：首版文章不填写原生 frontmatter `id`，默认 doc ID 只由当前构建内部消费。本站不得手工拼接或提交 doc ID 可编辑映射，也不得将其作为跨构建、跨发布或领域服务的持久身份；Docusaurus 在当前临时目录与静态构建制品中的框架内序列化不构成本站真相源。文章正文链接到同一 docs 实例内的另一篇文章时，必须使用带目标实际 `.md` 或 `.mdx` 扩展名的源码相对文件路径；不得使用 articleId 自定义协议、doc ID 或硬编码公开 slug。源码目录或正文扩展名变化时，同一变更必须更新全部入站链接并通过断链检查。技术分享侧栏由官方 `sidebarItemsGenerator` 在构建期复用 D-060 文章成员结果，并读取已校验的 `publicationStatus`、`classification` 和插件提供的当前 `docs[].id`，生成 `type: 'doc'` 项；生产只生成 `published` 与 `archived` 文章项，`draft` 不进入生产侧栏，不得用框架默认行为代替本站可见性门禁。生成器不得按物理目录、articleId、slug 或自建成员清单反推分类，不手写或提交第二份 doc ID 成员清单。开发预览显示独立 draft 分组并强制 `noindex`；公开排序和显示名按 E-003，生成器接口、错误格式和契约测试按 D-078 写入编码 Spec。

普通技术文章默认使用 Markdown。只有确实需要文章专属组件、且普通 Markdown 无法满足时才使用 MDX；MDX 只能从 `src/components/mdx/index.ts` 导入仓库内经过审核的 React 组件。M0 白名单初始为空，因此首版不得创建 MDX 文章；后续增加组件时必须同时记录用途、浏览器行为、外部请求、数据处理和失败退化。文章局部素材放在同目录 `assets/`；项目主预览原件进入 `site-assets/projects/<project-id>/`，始终公开的品牌和根级文件进入 `static-public/`。符号链接、越界路径、大小写冲突、未登记项目预览和生产白名单外文件必须让门禁失败；原件与始终公开目录都只经 E-008 的受控入口投影，不把整个项目素材目录直接交给 Docusaurus。

技术文章已通过 D-036 选择完整编辑模型，能力范围覆盖核心发布信息、作者、项目与模块组织、主题标签、系列关系、SEO 覆盖、推荐控制和公开修订记录。D-037 进一步确认元数据与正文保存在同一个 Markdown 或 MDX 文件中，少量核心字段位于 frontmatter 顶层，复杂且可选的元数据按职责嵌套分组，不使用文章级 sidecar 文件。D-038 至 D-050 已确认核心字段、受控 SEO 描述覆盖、显式日期、作者注册表、“项目-模块-主题标签”的组织基数及 `classification` 唯一分组；D-064 又确认顶层 UUIDv7 articleId 的领域身份职责。其中 D-035、D-038 的文章字段值与映射语义已被 D-058 部分替代。注册表与剩余 M0 字段按 E-003 和[站点体验设计](../product/site-experience.md)执行，框架投影按 D-059，不再建立第二份原生字段真相源。

`authors` 引用 `docs/contracts/authors.json` 中的单一对象，作者 ID 是对象键。首版作者记录必填 `displayName`，`links.github` 可选；`lyty1997` 的初始显示名同为 `lyty1997`，GitHub 地址为 `https://github.com/lyty1997`。首版不加入简介、头像、其他社交链接或作者详情页。个人作者、Axial Muse 站点品牌、未来发布组织和未来中央账户互不替代。

`summary` 是目录摘要、正文导语、默认 meta description 和默认分享描述的单一来源。只有普通摘要无法满足时才填写 `seo.description` 或 `seo.socialDescription`；后者按自身、`seo.description`、`summary` 的顺序回退。禁止新增 `excerpt`、从正文自动截取、在页面组件硬编码第二份摘要，或提交空白及与回退值完全相同的冗余覆盖。新增覆盖必须在评审中说明原因，正文、标题或摘要发生实质修改时必须复核已有覆盖。

`publishedAt` 与 `updatedAt` 使用 `YYYY-MM-DD`。`draft` 不得填写 `publishedAt`，可选 `updatedAt` 且不公开；`published` 和 `archived` 必须同时填写，首次发布时两个日期相同，之后 `publishedAt` 保持不变。发布辅助命令是独立于 D-065 文章创建命令的作者操作，按 `Asia/Shanghai` 写入源文件，修改随正文进入 Git diff；创建命令不自动调用发布命令，也不从 UUID 时间填写日期或自动发布。CI、Docusaurus 和生产服务器只读校验，不在构建或部署时注入时间。公开文章跨日期发生可见修改时必须更新 `updatedAt`，迁移旧文章可在提交前手工填写真实历史日期。UUIDv7 的 UTC 技术时间不得覆盖、补齐或校验这两个显式日期；未来按日期查询或排序也只能消费这两个领域字段。

技术文章不使用通用主分类。组织字段只存放在必填的 `classification` 对象中：`classification.project` 和 `classification.module` 均可为空且各最多一个；`classification.module` 只能与 `classification.project` 同时存在，并必须引用该项目所属模块。只有项目的文章进入项目根级，两者均为空的文章进入独立通用分组。`classification.topics` 必填 1-5 个受控主题 ID。跨项目文章只选择一个主项目，其他项目关系不得使文章在多个项目侧栏重复出现。项目、模块和主题的稳定 ID 引用 Git 注册表，显示名称与 ID 分离；这些关系不进入 URL，重分类也不修改 URL。

构建门禁必须拒绝缺少 `classification`、孤立模块、模块与项目归属不一致、主题为空、主题超过 5 个、未登记 ID，以及同一文章被配置到多个规范目录位置；还必须拒绝在 frontmatter 顶层或 `relations`、`taxonomy` 等其他分组中重复定义项目、模块或主题组织字段。项目及模块由 `docs/contracts/projects.json` 管理，作者和主题分别由 `docs/contracts/authors.json`、`docs/contracts/topics.json` 管理；无项目文章显示在虚拟分组“通用技术”，跨项目关系只使用可选 `relations.projects`，且不改变规范侧栏归属。

### MDX 使用门禁

每次新增或修改 MDX 文章时，评审必须明确：

- 为什么普通 Markdown 无法满足该文章。
- 引用了哪些仓库内组件，以及这些组件的审核记录。
- 组件是构建时静态输出还是需要浏览器端交互。
- 是否新增浏览器 JavaScript、外部请求、用户数据或第三方依赖。
- 组件失败时是否仍能阅读文章的核心内容。

允许使用 MDX 不代表批准任意 UI 框架、远程模块、第三方脚本或客户端加载策略。对应需要出现时，必须先完成独立决策。

### 迁移前的当前状态

当前仓库尚未引入 Docusaurus。`docs/contracts/projects.json` 当前保存项目结构化事实，并继续作为迁移后的项目领域来源；`site-content/projects/<project-id>/index.md|index.mdx` 只保存长篇正文。`public/index.html` 是迁移前的手写发布结果，迁移完成后停止人工同步 contract、HTML 与项目正文中的同一字段。

迁移必须保留 Git 历史、发布日期和旧 URL 语义。技术文章 `slug` 由作者按 D-058 直接填写为 Docusaurus 原生根相对完整路径，是公开 URL 的唯一真相源；不得从 articleId、文件名、目录、标题、日期、分类或系列生成，也不得再生成第二个框架路由字段。构建时必须校验格式和全站路由唯一性。发布后如需修改，必须在同一变更中增加旧 URL 永久重定向并更新 canonical URL 与站点地图；articleId 保持不变。E-014 已固定由同一 production payload 派生服务端 301：旧 source 及其无斜杠别名直接到 payload 中实际存在的最终 200 页面，不生成静态跳转 HTML，并与页面整版激活和回滚。当前已确认核心字段、UUIDv7 articleId、作者显式仓库 Node.js 创建入口与一次性 ID 写入、Node 24 LTS 原生 UUIDv7 后端、精确版本治理、组织语义、原生文章 slug、最小内存适配、`writing/` 文章类型边界、仓库根 `site-content/` 物理内容根、每文独立源码目录、稳定可读的 `<source-name>`、源码相对文章链接、侧栏身份引用，以及 E-013 的完整历史范围、复用语义和失败边界。#23/#26 已完成内容 schema、只读投影、派生索引、双侧栏、路径门禁和 production build 装配并进入当前精确基点；D-097 的完整历史检查器、临时 Git DAG fixture 与 Node 24 CI 接线已依 D-100 纳入专题分支。#24 的作者创建命令也已通过临时完整 Git fixture，并依 D-103 获准纳入当前专题分支提交及同名临时 ref；旧文一次性分配、文章素材和服务端规则生成器仍未完成，真实主题注册表也仍为空，因此本轮不创建真实文章文件或宣称远端闭环。

## 内容状态

> D-040 确认下表为技术文章 `publicationStatus` 的完整枚举。项目发布状态和项目体验状态属于独立模型，不受本表改变。

| 状态 | 含义 | 是否公开 |
|---|---|---|
| `draft` | 正在写作，事实与结构尚未完成审核 | 否 |
| `published` | 已通过审核并进入生产站点 | 是 |
| `archived` | 不再维护但保留历史价值 | 是，并明确归档状态 |

生产构建不得为 `draft` 生成列表项、正文路由或 sitemap 条目。`planned` 只作为 Issue、路线或选题记录，不进入文章集合，也不占用文章 slug 或 URL。`archived` 正文保持公开，并明确标注不再维护。

## 选题与优先级

首版内容围绕真实项目产生，按以下顺序排序：

1. 能解释一个已遇到的问题和真实约束。
2. 有可展示的设计、代码、实验或复盘证据。
3. 对后续项目决策或读者实践有复用价值。
4. 能与现有项目或系列形成清晰关系。

只有观点、没有验证材料的内容可以发布，但必须明确标注为观点，并说明推理范围。涉及外部事实时优先链接官方文档、标准、论文或原始公告。

## 内容模板

### 技术分享

1. 标题与摘要。
2. 问题背景：为什么需要解决。
3. 约束与非目标：本次没有解决什么。
4. 方案选择：考虑过哪些路径，为什么选择当前方案。
5. 实现或实验：给出可复核步骤和必要代码。
6. 验证结果：说明通过、失败和没有覆盖的部分。
7. 复盘：哪些结论可复用，哪些只适用于当前项目。
8. 参考来源与更新时间。

### 项目详情

1. 项目摘要与当前状态。
2. 目标用户或使用者。
3. 核心问题与边界。
4. 架构和关键决策。
5. 当前成果与证据链接。
6. 已知限制与风险。
7. 相关技术分享。
8. 最近更新时间与下一阶段。

## 发布工作流

1. **建立记录**：为选题创建 Issue 或路线条目，写明目标读者、问题、证据来源和内容状态。
2. **创建文章**：由作者在获准的 Linux 作者环境中使用与仓库 `.nvmrc` 精确一致的 Node，显式运行 CODE-014 固定的 `node scripts/author/create-article.mjs ...`，并一次性提供 source-name、title、完整 slug、summary、1-4 个已登记 author、1-5 个已登记 topic 及可选 project/module。成功后先确认 Git diff 只新增目标文章目录及唯一 `index.md`，再继续编辑；最低版本兼容任务不能代替正常作者入口。当前实现仍未提交，且真实 topic 注册表为空，所以首次真实使用前还必须先按内容决策登记获批主题，不能复制临时 fixture ID 或手工模拟模板。
3. **起草**：修改正文与作者确定的领域字段；事实、观点、计划和未知信息使用不同表达，不从 articleId 推导 slug、分类或日期。
4. **自检**：检查真实姓名、联系方式、截图、日志、路径和示例数据，移除密钥与隐私信息。
5. **准备发布**：D-047 发布辅助命令实现后，首次公开或公开修订时由作者在获准的 Linux 执行环境独立触发该日期操作并审查日期 diff。当前不得把未实现的命令写成可用工具，文章创建命令也不承担该步骤。
6. **验证**：完成 Docusaurus 迁移后，在完整非浅 Git worktree 的 Linux 环境或 Ubuntu CI 中分别通过 E-010 `run-script` profile 运行 `quality`、D-074 的独立 `tsc --noEmit`、E-012 的 Node ESM 测试、E-013 的完整历史门禁和 Docusaurus build，再启动预览并通过浏览器检查桌面端、平板端、移动端、链接和资源；涉及既有 slug 时还要证明 E-014 注册表能从同一 production build 派生唯一 301、目标页面存在且 source 没有静态 HTML。预览、类型检查、测试、历史检查、静态构建与 release 检查互不替代。D-097 至 D-099 已在当前工作区把 `quality`、`typecheck`、Node ESM 测试、完整历史与 production build 接入 Node 24 主/最低端点并通过本地 fresh 验收；预览、真实浏览器、release/production artifact、远端 CI 与部署检查仍未闭环，不得从本地门禁通过推导生产就绪。
7. **创建 PR**：说明设计文档依据、公开内容变化、来源、截图和验证结果。
8. **预览审核**：使用分支预览确认排版、导航、SEO 元数据、图片和索引策略。
9. **内容审核**：逐项核对标题、摘要、事实来源、状态、日期、版权和承诺边界。
10. **发布**：变更先提交并推送到 `dev`；集成验收通过后创建 `dev -> main` PR，Ubuntu CI required checks 通过再合并，由生产部署自动上线。禁止直接 push `main`。
11. **上线核验**：检查生产 URL、canonical、分享卡片、关键链接和实际部署提交。
12. **记录**：在 [项目进度](../progress.md) 记录发布时间、提交、URL、验证和遗留问题。

任何一步失败都保留真实错误并修复根因，不通过跳过门禁或手工覆盖生产文件完成发布。

## 审核清单

### 可信度

- 标题和摘要与正文结论一致。
- “已完成”“已验证”“可用”等表述有对应证据。
- 推测、个人观点和未来计划没有写成客观事实。
- 外部引用链接到原始出处，引用范围符合版权要求。

### 隐私与安全

- 截图已检查浏览器标签、用户名、主机名、路径、邮箱、通知和后台标识。
- 示例凭证为明显无效占位符，不接近真实密钥格式。
- 不公开客户、内部沟通、未授权数据或未公开商业计划。
- 外部嵌入、分析脚本和表单没有随内容修改被悄然引入。
- 项目预览在进入 Git 前已经确认可公开；preview 构建的状态隔离不被当作保密、凭证或版权边界。

### 可维护性

- articleId、slug、标题、摘要、发布状态和日期符合已确认的内容模型；E-013 从完整非浅 HEAD 可达历史证明 articleId 与 source-name 未改绑或删除后重引，稳定注册表 ID 也未删除后重引。
- 新文章由作者在获准的 Linux 作者环境显式运行仓库内创建命令建立，创建结果经 Git diff 审查；Git hook、CI、构建和发布没有生成、修复、暂存或提交 articleId。
- `classification.project`、`classification.module` 和 `classification.topics` 中的 ID 均能在对应注册表中解析。
- `classification.module` 只在 `classification.project` 存在时填写，并且隶属所选项目。
- `classification.topics` 存在且包含 1-5 个主题 ID。
- 每篇文章只生成一个规范目录条目，跨项目相关关系不产生重复侧栏入口。
- 图片有来源、替代文本和合理尺寸。
- `published`、`archived` 项目恰有一个符合 E-007 的 `previewImage`；源文件只位于自身 `site-assets/projects/<project-id>/`，登记尺寸、文件字节和公开路径一致。
- 同一 docs 实例内的文章链接使用带实际 `.md` 或 `.mdx` 扩展名的源码相对文件路径，没有使用 articleId 自定义协议、doc ID、硬编码公开 slug、本机绝对路径或预览域名。
- 发布日期和更新时间含义正确，不用小修改伪装成新发布。
- 已发布 slug 如有修改，同一变更登记非空原因，旧路径和无斜杠别名都单跳新的 canonical 页面；目标页面存在，旧路径不生成静态 HTML，查询串测试通过。二次迁移还要证明生产暴露账本中的每个历史 source 与历史 target 都解析到同一个当前 200 终点。

## 图片与附件

- 优先使用本人项目的真实截图、架构图和必要的演示素材。
- 第三方图片必须有明确授权或符合许可，仓库记录来源和许可信息。
- 发布前移除 EXIF 等不必要元数据，压缩到满足清晰度的最小尺寸。
- 图片文件名使用可读的 ASCII slug；同一内容的多尺寸版本保持一致命名。
- 不上传包含真实凭证、私人账号、未公开域名或内部网络信息的素材。
- 项目主预览不放入 `static-public/` 或 Docusaurus 原始 `static/`；`draft`、`planned` 素材即使只用于局域网预览，也按可能随 Git 公开的材料审核。

## 修订、纠错与归档

小型文字修正直接更新 `updatedAt`；影响结论、步骤或安全性的修改，在正文增加简短修订说明。发现高风险错误时先从导航和列表移除或添加醒目标记，再完成修复，不让错误内容继续作为当前建议传播。

项目、模块或主题关系发生变化时，只更新组织引用和必要的 `updatedAt`；不得改写或重新生成 slug、canonical URL 或公开 URL，也不得为同一文章新增第二个规范目录入口。

永久重定向不是普通可逆内容改动。301 一旦对外返回，浏览器和中间缓存可能长期记住新目标；root-owned 生产暴露账本因此必须在 reload 前只追加候选的全部规范路径和可能暴露的 registered 301 边。`canonical-slash` 不单独入边账本，但它指向的 canonical target 必须随候选规范路径预写，不能等公网冒烟后才登记。后续候选必须让每个历史路径仍为 200 或单跳当前 200，并让每条历史边的 source 与历史 target 收敛到同一终点。生产回滚不能只检查目标文件存在：缺少历史 source 规则、让旧 target 404 或把两者导向不同页面的 release 都不兼容。新增 canonical URL 或永久边没有兼容 fallback 时默认停止发布；首次发布新 URL 通常因此需要单独授权 forward-only，授权后只能发布保持完整历史闭包的向前修复版本。

内容不再适用但仍有历史价值时转为 `archived`，说明原因和替代内容。除隐私、版权、安全或法律原因外，不直接删除已被外部引用的 URL；使用归档页或永久重定向保存链接语义。

## 发布节奏

M0 以完成 2 个可信项目条目、真实视觉证据和不虚构文章的技术分享空状态为上线内容基线。完整技术分享采用“完成即发布、每月复盘”的增量节奏，不阻塞主站首次上线，也不设置为了数量而发布的硬指标。月度复盘检查内容状态、失效链接、过时结论和下一批选题。
