# 内容发布流程

状态：active
最近更新：2026-07-13
适用范围：M0-M2 项目、技术分享和页面文案的创建、审核、上线与修订

## 目的

本文定义内容从想法到生产发布的可追溯流程。目标不是提高发布数量，而是保证每项公开内容有来源、有状态、能修订，并与站点代码通过同一 Git 工作流发布。

## 内容真相源

M0 按内容类型划分所有权：`docs/contracts/projects.json` 是项目标题、状态、日期、仓库、展示模式和技术取舍的事实真相源；`public/index.html` 是实际公开页面结构与页面级文案的发布真相源；`docs/` 中的产品和架构文档定义两者的边界与显示规则。

由于 M0 不使用生成器，项目事实会人工映射到 HTML。每次修改必须在同一个 PR 中同步 contract、HTML 和站点门禁；CI 校验已发布项目的关键字段和链接。内容规模触发[M0 技术选型决策](../architecture/technology-selection.md)中的重新选型条件后，改为由结构化内容生成页面，不继续扩大人工双写。

在引入结构化站点框架前，不新建独立 CMS、数据库或在线表格作为第二真相源。

进入 M1 时，内容文件应迁移到仓库内统一的结构化目录，并由构建过程生成公开页面；具体格式在框架选型时决定。迁移必须保留 Git 历史、稳定 slug、发布日期和旧 URL 重定向。

## 内容状态

| 状态 | 含义 | 是否公开 |
|---|---|---|
| `draft` | 正在写作，事实与结构尚未完成审核 | 否 |
| `planned` | 已列入公开路线，但正文尚未发布 | 只可作为计划简述 |
| `published` | 已通过审核并进入生产站点 | 是 |
| `archived` | 不再维护但保留历史价值 | 是，并明确归档状态 |

公开页面不得链接到仅存在于仓库的草稿文件。`planned` 只能描述方向和边界，不能伪装成可阅读的完整内容。

## 选题与优先级

首版内容围绕真实项目产生，按以下顺序排序：

1. 能解释一个已遇到的问题和真实约束。
2. 有可展示的设计、代码、实验或复盘证据。
3. 对后续项目决策或读者实践有复用价值。
4. 能与现有项目或系列形成清晰关系。

只有观点、没有验证材料的内容可以发布，但必须明确标注为观点，并说明推理范围。涉及外部事实时优先链接官方文档、标准、论文或原始公告。

## 内容模板

### 技术分享

1. 标题与摘要。
2. 问题背景：为什么需要解决。
3. 约束与非目标：本次没有解决什么。
4. 方案选择：考虑过哪些路径，为什么选择当前方案。
5. 实现或实验：给出可复核步骤和必要代码。
6. 验证结果：说明通过、失败和没有覆盖的部分。
7. 复盘：哪些结论可复用，哪些只适用于当前项目。
8. 参考来源与更新时间。

### 项目详情

1. 项目摘要与当前状态。
2. 目标用户或使用者。
3. 核心问题与边界。
4. 架构和关键决策。
5. 当前成果与证据链接。
6. 已知限制与风险。
7. 相关技术分享。
8. 最近更新时间与下一阶段。

## 发布工作流

1. **建立记录**：为选题创建 Issue 或路线条目，写明目标读者、问题、证据来源和内容状态。
2. **起草**：在功能分支修改内容；事实、观点、计划和未知信息使用不同表达。
3. **自检**：检查真实姓名、联系方式、截图、日志、路径和示例数据，移除密钥与隐私信息。
4. **本地验证**：运行 `npm run quality`，启动本地预览并检查桌面端、平板端、移动端、链接和资源。
5. **创建 PR**：说明设计文档依据、公开内容变化、来源、截图和验证结果。
6. **预览审核**：使用分支预览确认排版、导航、SEO 元数据、图片和索引策略。
7. **内容审核**：逐项核对标题、摘要、事实来源、状态、日期、版权和承诺边界。
8. **发布**：变更先提交并推送到 `dev`；集成验收通过后创建 `dev -> main` PR，required checks 通过再合并，由生产部署自动上线。禁止直接 push `main`。
9. **上线核验**：检查生产 URL、canonical、分享卡片、关键链接和实际部署提交。
10. **记录**：在 [项目进度](../progress.md) 记录发布时间、提交、URL、验证和遗留问题。

任何一步失败都保留真实错误并修复根因，不通过跳过门禁或手工覆盖生产文件完成发布。

## 审核清单

### 可信度

- 标题和摘要与正文结论一致。
- “已完成”“已验证”“可用”等表述有对应证据。
- 推测、个人观点和未来计划没有写成客观事实。
- 外部引用链接到原始出处，引用范围符合版权要求。

### 隐私与安全

- 截图已检查浏览器标签、用户名、主机名、路径、邮箱、通知和后台标识。
- 示例凭证为明显无效占位符，不接近真实密钥格式。
- 不公开客户、内部沟通、未授权数据或未公开商业计划。
- 外部嵌入、分析脚本和表单没有随内容修改被悄然引入。

### 可维护性

- slug、标题、项目关系和状态符合内容模型。
- 图片有来源、替代文本和合理尺寸。
- 内部链接使用站点约定路径，没有链接到本地文件或预览域名。
- 发布日期和更新时间含义正确，不用小修改伪装成新发布。

## 图片与附件

- 优先使用本人项目的真实截图、架构图和必要的演示素材。
- 第三方图片必须有明确授权或符合许可，仓库记录来源和许可信息。
- 发布前移除 EXIF 等不必要元数据，压缩到满足清晰度的最小尺寸。
- 图片文件名使用可读的 ASCII slug；同一内容的多尺寸版本保持一致命名。
- 不上传包含真实凭证、私人账号、未公开域名或内部网络信息的素材。

## 修订、纠错与归档

小型文字修正直接更新 `updatedAt`；影响结论、步骤或安全性的修改，在正文增加简短修订说明。发现高风险错误时先从导航和列表移除或添加醒目标记，再完成修复，不让错误内容继续作为当前建议传播。

内容不再适用但仍有历史价值时转为 `archived`，说明原因和替代内容。除隐私、版权、安全或法律原因外，不直接删除已被外部引用的 URL；使用归档页或永久重定向保存链接语义。

## 发布节奏

M0 以完成 2 个可信项目条目、真实视觉证据和不虚构文章的技术分享空状态为上线内容基线。完整技术分享采用“完成即发布、每月复盘”的增量节奏，不阻塞主站首次上线，也不设置为了数量而发布的硬指标。月度复盘检查内容状态、失效链接、过时结论和下一批选题。

## 验收标准

- 每项公开内容有状态、更新时间、负责人和可追溯提交。
- 技术分享包含问题、约束、取舍、验证和来源。
- 发布只能由 Git 合并触发，生产内容与 `main` 一致。
- 上线前完成质量、渲染、隐私、版权与链接检查。
- 修订和归档不会破坏已有 URL 或隐藏重要历史变化。
