## 方案选择

| 方案 | 可证明的边界 | 影响与代价 |
|---|---|---|
| A：服务器 root 临时启用合成资源失败，推荐 | 服务器合成样本判定、编码、实际 TAT、runner 非零、真实通知及恢复 | 新增严格受限的本机管理入口、短期控制状态与演练封套；需要认证安装 |

## 控制入口与有效期

候选 root 管理命令 `axialmuse-resource-drill` 提供三种操作：

| 操作 | 输入与效果 |
|---|---|
| `--arm --scenario <枚举> --ttl-seconds <秒> --authorization-id <ID>` | 生成随机 128 位 `drillId`，绑定当前运行时、活动 release、账本摘要、boot ID、UTC 与开机经过时间；完整落盘后发布活动标记 |
| `--status` | 输出控制标记的演练 ID、请求摘要、场景、时效/停用状态与剩余秒数；无活动标记时返回 inactive，并列出保全的停用 ID 与回执摘要 |
| `--disarm <drillId>` | 先持久化该 ID 的停用事实，再移除匹配的活动标记；保留请求与停用回执，重复停用同一 ID 幂等 |

`scenario` 只允许 `disk-used-warning`、`disk-used-critical`、`disk-free-warning`、`disk-free-critical`、`inode-used-warning`、`inode-used-critical`。每种映射到一份仓库内固定合成样本，调用现有 `check_resources()` 计算预期稳定码；不接受任意失败码、路径、命令、Python 表达式或容量参数。合成样本没有真实容量信息。

本地入口及封闭格式：`ops/maintenance/resource_drill_command.py` 经稳定启动器的 `axialmuse-resource-drill` 入口执行；`--arm` 与 `--disarm` 返回包含 `request`、`requestSha256`、`receipt`、`disarmReceiptSha256` 的私有记录。未停用时后两项为 null。`--status` 的 active 只表示标记和时间窗口有效，显式携带 `bindingVerified:false`，不冒充站点或运行时身份已复验；producer 仍在每次真实完整快照之后核验绑定。inactive 的 `disarmedRequests` 数组供独立回读核对停用事实，不需要健康 release 或加载 verifier 模块。

候选 TTL 为 1 至 1,800 秒，演练默认 1,800 秒。同时核验同一 boot、`CLOCK_BOOTTIME` 截止值及 UTC 窗口；当前 UTC 早于创建时间、越过任一截止时间、发生重启或合法绑定身份已变化时不再注入。开机时间数值回退视为控制状态异常。时钟异常不能延长窗口，过期请求不能重新 arm；重新演练必须生成新 ID，不自动续期或重试。该失效由读取端判断，不依赖清理定时器执行。

同一时刻只允许一个活动请求。相同授权 ID 的重放只能返回已落盘的原请求，不能刷新 ID 或期限；参数变化、其他活动请求或未知残留明确拒绝。管理命令核验有效 UID 为 root，包装器和启动器参与完整源码认证；不增加受限监测用户的 sudo 权限。

## 状态与中断边界

控制目录候选为 `/var/lib/axialmuse/resource-drills/`，root:root/0700；请求、活动标记和停用回执均为 root:root/0600、普通单链接文件。认证安装在切换新版入口前初始化该目录及版本 schema，与组合维护的状态和启用开关分离；初始无活动请求。新版入口必须要求该完整结构存在，缺失或异常报错，不能把整个状态目录丢失解释为从未启用演练。旧运行时不读取该新目录。

请求包含 `schema`、`drillId`、`authorizationId`、`scenario`、`runtimeSha256`、`siteIdentity`、`ledgerSha256`、`bootId`、`createdAtUtc`、`expiresAtUtc`、`startedBoottimeNs` 和 `deadlineBoottimeNs`。字段与类型完全封闭，JSON 重复键、未知字段和异常长度均拒绝。活动标记只绑定 `drillId` 与规范请求字节的 SHA-256，不直接承载可变配置。

管理与快照读取使用相同锁序：生命周期锁、verifier 锁、部署锁、演练状态锁；不允许持后级锁再等待前级锁。arm 在锁内重验绑定身份和健康前态，按准备、同步、不可覆盖发布请求、同步、发布活动标记、同步的顺序写入。半写准备目录不产生注入语义；没有活动标记的完整请求也不产生注入语义。

disarm 必须核验目标 ID 和摘要，先原子发布并同步停用事实，再移除活动标记并同步目录。停用事实已存在而活动标记尚未移除时，读取端停止注入，管理端可续完该次停用。停用不要求真实资源或 release 已恢复健康，也不要求当前身份仍匹配原绑定；这些是停止演练后重新验收的内容。未知 ID、摘要漂移或未知成员停止并保留现场，不能用清空目录修复。

停用回执精确包含 `schema`、`drillId`、`requestSha256`、`disarmedAtUtc`、`bootId` 和 `disarmedBoottimeNs`；后两项仅留服务器私有控制目录。重复 disarm 返回原回执，不改写原停用时间。操作会话保存回执摘要及独立 status 读取结果，作为后续恢复记录的停用依据；inactive 只说明控制未生效，不证明已发出的结果或工作流均已结束。

只读监测入口仅读取控制状态，不消费请求、不写计数或回执；一个有效窗口内的重复调用均失败。请求控制数据合法但已到期、停用或绑定身份变化时正常回到真实检查；类型、权限、摘要、结构或读取异常则返回 `MONITOR_DRILL_STATE`，不能把损坏状态当成演练关闭。启动器完整性失败仍走原失败路径。

## 失败进入真实链路的位置

1. 正常调用真实 `check_resources()`，完成原有活动 release、维护状态与账本校验。任何真实失败都保留原失败码并中止，不能被标成演练。
2. 在同一锁和已验证快照身份内读取控制状态；仅有效请求可触发固定合成样本的第二次资源判定。生产真实读数从不被替换。
3. 合成判定必须精确得到该场景的预期失败码；意外正常或其他结果返回 `MONITOR_DRILL_FIXTURE`，不能直接伪造预期错误。
4. 返回严格区分演练的封套，经过原固定命令和实际 TAT 传输。该封套不表示活动快照或资源健康，不进入正常基线构造。
5. runner 校验封套、来源、时效和字段后生成失败回执、日志定位信息及 job summary，进程退出 1，workflow 实际结论必须为 failure。不能使用 `continue-on-error`，也不能把预期失败转成绿。

候选演练封套精确包含 `schema:2`、`observedAtUtc`、`resourceFailure` 和 `drill`。`drill` 精确包含 `id`、`scenario`、`requestSha256`、`runtimeSha256`、`siteIdentity`、`ledgerSha256` 和 `simulated:true`。真实资源故障继续采用原 schema 1，不携带 `drill`。runner 依据本次已认证 TAT 结果处理 schema 2，要求时间新鲜、身份符合下节契约、场景与失败码一一对应；未知版本、类型错误、缺项、额外项或输出截断均失败。

封套不传 boot ID、授权 ID、真实容量、服务器路径、日志正文或凭证。GitHub run ID/attempt、触发者及 event 由 Actions 上下文获取，不依赖通知邮件正文承载全部字段。

封套验证失败仍使 workflow 失败，但不能计为预期演练成功。真实故障与演练共享传输，新增错误分支不削弱原来的认证、退出状态或新鲜度要求。

### 三种身份的来源与校验

| 身份 | 来源与字段 | 校验关系 |
|---|---|---|
| 活动站点 | `siteIdentity` 来自锁内通过验证的活动 release 收据，精确沿用正常基线 identity 的五个字段：`workflow_run_id`、`artifact_id`、`commit_sha`、`artifact_digest`、`release_content_sha256` | arm 记录完整身份与 `ledgerSha256`；producer 每次注入前重验二者与请求相同；已有健康基线的 runner 也逐项比较 |
| 监测运行时 | `runtimeSha256` 来自认证稳定启动器固定的实际不可变模块根摘要，不取自站点 SHA 或输入参数 | producer 与请求绑定值比较；演练验收再与独立安装回执中的运行时摘要比较；运行时切换使旧请求失效 |
| workflow 源码 | `workflowSourceSha` 来自 Actions 上下文的 `GITHUB_SHA`，并与已核验 checkout HEAD 一致；不由服务器封套提供 | 记录本次运行源码身份及对应 CI，验证 runner 的来源；不要求等于活动站点 `commit_sha`，也不要求等于运行时摘要 |

`siteIdentity` 复用现有 identity 的字段、类型和长度校验；两个摘要为 64 位小写十六进制。首次读取就收到演练封套时，runner 尚无健康基线，只能依据已认证传输、封闭结构与新鲜度接受一份失败诊断，不能将封套自报身份当作独立健康证明。操作会话将失败回执与 arm 请求、健康前态及安装回执比对，三者匹配才计为预期演练。后续读取收到演练封套时，还必须匹配该 run 已建立的站点身份与账本；不匹配按身份漂移失败，不标记为合格演练。

daily/weekly 允许当前 main 已前进而活动站点仍为较早 release；每次真实快照的既有一致性校验继续适用。monthly 原有质量验证要求 checkout SHA 等于活动站点 SHA，该单独门禁继续执行；上述身份区分不放宽它。反例须覆盖前两种周期的正常 SHA 差异、错误站点身份、错误账本、运行时切换，以及伪造 workflow 源码身份。

### 每次读取的演练证据传播

所有服务器读取共用一次运行内的诊断收集器；在认证传输完成后统一验证封套及本次读取时效，再决定返回健康快照还是抛出带结构化诊断的失败。诊断随异常对象的显式字段传递，不从 `str(error)`、stderr 或任意异常属性恢复；无效封套只保留固定校验失败码，不能取得合法演练身份。阶段枚举为 `bootstrap`、`before`、`after`、`monthly-final`，分别覆盖首次取基线、组合探测前后和月度质量结束后的读取。

候选传输接口 `TatTransport.fetch_observation()` 返回有效载荷与本次认证调用证据，原 `fetch()` 的正常载荷契约可保留给既有调用者。调用证据来自传输层已验证的 invocation 和唯一任务身份，不从载荷自报字段取得；即使返回失败诊断，也必须经过原任务终态、命令内容、退出码、完整输出和新鲜度校验。原始云资源标识仅在操作会话的私有记录中关联，不写共享日志或工件；公开回执使用该证据规范字节的摘要 `transportEvidenceSha256`，私有证据不包含密钥或完整云响应。

调用证据精确包含 `schema:1`、`invocationId`、`commandId`、`instanceId`、`createdTime`、`commandSha256` 和 `outputSha256`；后两项为已验证命令及解码输出原始字节的 SHA-256。前三个 ID 与创建时间来自已验证的云任务，字段沿用传输层校验。操作会话通过现有授权的云任务只读结果重建该最小记录并核对公开摘要，避免只发布不可回查的摘要，也无需把原始云标识暴露到日志。查不到或摘要不符则关联未验收。

`fetch_observation()` 返回精确的 `{payload, evidence}`；兼容 `fetch()` 仍只返回 payload。createdTime 规范化为 UTC 的 ISO 时间（保留原解析精度）；最小证据摘要采用 `ops.monitor.public_health.canonical()` 的排序紧凑 JSON 字节（含末尾 LF）。outputSha256 始终针对解码后的原始输出，不针对重序列化的 payload。服务器请求与停用事实沿用 `deployment_state.canonical()`；请求摘要由其已保全原始文件字节计算，不能混用两种序列化格式。

run 回执新增 `workflowSourceSha` 与按发生顺序记录的 `serverReadEvidence` 数组，每项精确包含 `phase` 和 `transportEvidenceSha256`。runner 还在首次 bootstrap 认证读取前固定 `startedAtUtc`，与公网采样的 `observedAtUtc` 分开保留；恢复时按[主设计](resource-alerts.md#人工事件记录入口与本地样例)从该开始时间验证新鲜度，不能接受核对前已启动但公网采样较晚的在途 run。所有通过认证及封套校验的健康读取、真实资源失败或演练读取均登记，正常恢复 run 的三次读取因此也能与云任务关联；传输或封套校验失败不登记为成功认证证据，其失败 check 仍须保留。真实失败的结构化诊断遵循[主设计](resource-alerts.md#真实失败的回执契约)。这些字段经 `public_receipt()` 白名单输出，操作会话在云任务证据仍可查询时及时取得私有记录。

每份合法诊断精确保留 `phase`、`observedAtUtc`、`resourceFailure`、完整 `drill` 与 `transportEvidenceSha256`。收集器按读取发生顺序追加，已记录条目不能被后续健康结果或其他异常覆盖。对应失败 check 附该诊断的规范字节摘要 `drillObservationSha256`；run 级 `drillObservations` 数组容纳全部条目，不能用单个顶层 ID 覆盖多次读取。若一个 run 跨越不同演练窗口，应分别保留各条证据，验收时分别归属。

新版 runner 的 run 回执始终包含 `drillObservations`，没有合法演练诊断时为空数组；恢复验收不能将该字段缺失解释为空。

`run_bound_sample()`、`run_period()` 以及 runner 顶层失败处理须保留此前所有检查；在返回组合回执或顶层失败回执后，由 runner 合入本次收集器条目，再交给 `public_receipt()` 做严格字段白名单过滤。日志和 summary 对每份合法诊断显示“受控演练”、阶段、ID、场景和稳定码；普通真实故障 check 不携带演练标识。演练不是允许忽略其他失败的理由，所有失败仍参与最终非零结论。月度末尾失败也必须保留已完成质量检查的结果。

实现验证须逐个阶段注入，并覆盖“首次健康、后续演练”“公网真实失败与 after 演练并存”“已记录演练后又发生真实故障”“两次读取诊断不同”“上层捕获异常及 public_receipt 过滤”“回执写失败”。每个反例同时断言非零、阶段与身份仍可定位、真实失败未被覆盖；回执写失败必须显式报告证据缺失，不能以日志代替完整演练验收。

## 通知与恢复闭环

通知沿用 GitHub Actions 的既有设置。[GitHub 官方规则](https://docs.github.com/en/actions/concepts/workflows-and-actions/notifications-for-workflow-runs)区分手动触发者和 schedule 的接收归属；修改 cron 或重新启用工作流还可能改变接收者。[账户设置](https://docs.github.com/en/subscriptions-and-notifications/how-tos/managing-github-actions-notifications)决定使用 Email 或 On GitHub，以及是否仅通知失败。实施前只读核对 actor 和工作流历史，维护者自行确认其接收设置，不读取邮箱正文或改动账户偏好。

| 环节 | 可验证的结果 | 不通过时的动作 |
|---|---|---|
| 健康前态 | 无活动标记；三种身份分别核验；CI 合格；真实资源检查及一次 fresh daily 成功；已建立在途调用清单 | 不 arm，先处理真实故障或补齐调用清单 |
| 启用控制 | 请求和状态回读一致，有效期有限，操作会话保留请求摘要 | 中断后核对状态；未知状态不盲目重发 |
| 触发失败 | 相同 ID/场景/稳定码到达 runner；回执正确，目标 run 为 failure | 撤销；保留实际错误，不计为演练通过 |
| 撤销控制 | 目标失败 run 结束后立即 disarm；保存绑定同一请求的停用回执与摘要，独立回读 inactive | 超时或 SSH 中断由 TTL 限制注入；后续仍须取得停用回执并独立核验状态 |
| 核对在途调用 | 窗口内可能已读取演练的 TAT、SSH 和工作流均已终结，证据完整归属 | 保持待核对；不启动下一轮，不宣告演练影响已结束 |
| 检查恢复 | 完成停用与在途核对后新发起 daily，真实检查路径成功且无演练标识；恢复记录绑定本次停用回执 | 保持未恢复；定位真实错误，不通过清理或回滚制造正常 |
| 确认通知 | 维护者提供“收到/未收到”及对应失败 run URL、渠道和大致时间 | 未收到或未确认则通知未验收；先核对接收设置和 actor，不自动重放 |
| 关闭演练 | 原始 failure、持久停用回执、在途核对结果、恢复 success、实际接收记录均齐全 | 缺失任一项保持未完成 |

撤销和恢复不等待用户确认通知；即使通知迟到或未送达，也必须及时结束注入。候选通知观察窗口为目标 run 结束后 15 分钟，超过后记录“本次窗口内未确认收到”，不解释为供应商承诺或永久丢失。接收确认只用于验收，不能清除失败记录或改变任何资源检查。既有设置若只通知失败，恢复以新成功 run 和回执确认，不承诺额外恢复邮件。

### 在途调用与恢复证据

本地新增独立手动候选 `.github/workflows/tat-read-only.yml`，仅目标仓库 main 运行，使用 maintenance 环境的既有监测凭证与实例变量；固定调用 `DescribeInvocationTasks`，隐藏命令输出并读完分页。日志仅包含 `visibleTaskCount` 与状态计数，未知状态、重复条目、实例不符、总数漂移或超时失败，原始云响应不上传。查询成功只说明该身份可见范围内的查询完成，不能以零条记录或零运行中任务自动认定完整在途核对通过；权限范围及实际调用归属仍须独立核验。该查询不调用监测快照，也不触发部署或演练；创建后须经独立 Git 交付才会出现在 Actions 手动入口。

停用只阻止随后取得控制锁的读取产生新演练诊断；撤销前已读取的输出仍可能在传输、runner 或通知队列中。`maintenance.yml` 的手动周期与自然 schedule 使用不同并发组，不能把目标 daily 结束当成其他运行均已结束。执行顺序固定为：持久停用并独立回读 → 核对可能受影响的在途调用 → 新发起恢复 daily → 归档恢复记录。通知可能迟到，接收确认独立记录，不阻塞停止注入。

arm 前，操作会话建立私有执行清单，记录当前 queued、waiting、in-progress 的 daily/weekly/monthly，以及已知管理 SSH 和尚未终结的固定 TAT 调用。清单持续补充至停用完成；从 arm 前已在途到停用边界内新出现的候选均纳入核对。停止发起额外演练请求或无关人工快照，但不暂停自然调度。使用现有授权的只读工作流、TAT 任务和管理会话证据核对完整性；若接口分页则读完相关页，读不到必要证据或清单无法确定完整时保持待核对，不扩大权限推断完成。

每项至少记录调用类别、私有调用身份、所属 run ID/attempt（适用时）、已知读取阶段、终态和是否命中当前 `drillId`。所有可能在停用前读取控制状态的候选必须有可验证终态：已完成者核对实际回执；取消或超时者还要核对其已发出 TAT/SSH 进程已终结，不能只看 GitHub 的 canceled 状态。停用前排队、停用后才开始的任务也需归档其真实结果。未知终态、缺少回执或未归属的调用均阻止本轮关闭；等待不能延长 TTL，也不自动重跑或取消其他工作流。

核对结束后再次独立读取控制状态，要求同一请求的停用事实仍在且没有新的有效演练，然后新发起恢复 daily。若为了尽早了解现场已在在途核对期间运行过健康检查，可保留为临时健康证据；它不能替代上述顺序中的最终恢复运行，额外 dispatch 需先核对执行预算。恢复 success 只证明该次真实读取与公网检查通过；它不撤销历史失败，也不保证邮件队列已经清空。

私有恢复记录精确包含 `schema`、`drillId`、`requestSha256`、`disarmReceiptSha256`、`inFlightEvidenceSha256`、`recoveryRunId`、`recoveryRunAttempt`、`recoveryWorkflowSourceSha`、`recoveryReceiptSha256` 和 `status`。`schema` 为整数 1，`drillId` 为 32 位小写十六进制，摘要为 64 位小写十六进制，源码 SHA 为 40 位小写十六进制，run ID/attempt 为正整数字符串；`status` 仅为 `pending` 或 `recovered`。pending 允许尚未取得的证据字段为 null，`drillId` 与 `requestSha256` 始终必填；recovered 不允许任何字段为 null。仅在恢复 run 满足顺序要求、结论为 success、完整回执为 passed 且 `drillObservations` 为空时置为 recovered。各证据摘要指向已保存的规范字节，不能只留不可解析的哈希。记录在操作会话的私有证据目录中以 0600 保存；恢复 runner 无需重新携带已停用的演练 ID。

恢复验收须比对 arm 前态、请求和恢复调用的认证证据中的活动站点身份与账本，并独立核对运行时仍为本轮认证版本。正常公开回执目前不直接携带账本摘要，故该比较使用关联到恢复 run 的真实 TAT 读取证据，不能仅凭其 passed 结论推断身份相同。发生合法发布、账本或运行时切换时，原请求依约失效；新的健康运行只记为新身份下的健康证据，不直接关闭原身份的恢复验收，需解释变化并重新审查。定向反例包括：恢复成功后旧 run 才报告演练失败、停用前排队但停用后才读取、任务取消后云调用仍在运行、时钟偏差导致时间排序不可靠、调用清单不完整、恢复期间重新 arm 及身份变化。顺序由持久停用回读和操作步骤建立，不能只比较服务器与 Actions 的墙钟时间。

最短实际执行为两轮，先 `disk-free-warning`，再 `inode-used-critical`，各自使用新 ID。先证明磁盘 warning 和 inode critical 均经过实际链路；其余阈值组合用定向 fixture 验证，证据明确该范围。两轮之间须有停用及恢复 success；第一轮恢复或通知确认未完成则不启动第二轮。

候选执行预算为一次健康前态 daily、两次失败 daily、两次恢复 daily，共最多五次手动 dispatch；不重跑原 failure，不自动补发。每次正常 daily 按当前链路读取三次快照，预期失败在第一次读取停止，合计预期最多 11 次 TAT invocation；实际次数和中断情况必须记录，超出预算先查明原因。自然 schedule 仍独立记录，不为演练改 cron、暂停日常监测或新增云命令。

无参数命令无法将请求只定向到某个 GitHub run：有效窗口内的 SSH 检查、手动或自然周期都可能看到同一演练失败。不能宣称“只影响目标 run”。实施前检查在途工作流并选择低重叠窗口，期间所有命中 run 都应按同一 ID 回填；若遇真实检查错误，它仍优先显示。窗口过期但目标任务尚未启动属于演练未触发，不延长期限制造通过。

自然 schedule 成功证明实际调度，手动 failure 的实际通知证明本轮接收。两种 event 的接收 actor 必须核对：一致时可将两份独立证据用于 #88 原清单验收，但不得宣称已经实测自然定时的失败通知；不一致时，原接收责任仍有缺口，需安排实际 schedule 失败及接收验证或先由所有者决定责任调整。排队延迟使有限 TTL 覆盖不到 schedule 时保持待验收，不自动扩大演练窗口。

## 发布、完成和残余边界

实施候选涉及 root 控制入口、稳定启动器入口表、运行时清单、服务器封套、runner 和对应回归。必须先 review、完整运维测试及现有质量门禁，再经批准的 Git 晋级流程取得精确 main CI；服务器按完整不可变组件协议认证升级，保留旧运行时及原状态。旧 runner 无法理解 schema 2，因此先交付兼容 reader、再安装 producer、最后显式 arm，默认关闭贯穿整个升级过程。

#88 单元 3 的演练验收需要：安装后自然 schedule、两轮实际 failure 与各阶段诊断回执、实际通知接收、两轮持久停用及在途调用核对、两次新发起的真实 daily 恢复与关联记录的完整证据。该证据只是[主设计完成标准](resource-alerts.md#完成标准与现有缺口)的一部分，不能替代真实事件接手、处置和关闭契约的验证。到期自动停止注入只是控制边界，不代表通知或恢复已验收。Issue #88 的日志、备份和组合维护单元继续独立推进。

本提案不提供 GitHub 调度缺席或 GitHub 自身通知故障的独立告警；发现任务未运行或通知未到，需要人工检查 Actions。增加第二通知供应商或外部心跳属于另外的责任和数据边界决定。本轮只实现并验证本地候选，不安装、不执行生产演练、不触发 workflow、不修改 Issue 勾选；没有新增第三方服务或用户数据处理。
