# 磁盘与 inode 真实告警闭环

状态：真实事件主流程及本地候选已实现；生产新增契约与演练待独立交付验收

最近更新：2026-11-24

适用范围：#88 单元 3，根文件系统容量与 inode；沿用 #41 认证只读监测、GitHub Actions 通知和个人维护责任。

## 目标与已确认边界

主要不变量：每个真实资源异常都保留可定位的失败证据，直到维护者接手、记录处置、独立确认恢复并明确关闭；后续成功不能擦除尚未处理的失败。

依据[本轮决定](../architecture/open-decisions.md#2026-11-23--88-真实资源告警闭环设计)，真实事件是本文主流程，[受控演练](resource-alert-drill.md)用于验证该流程的判定、失败传播、通知和恢复边界。演练请求、停用回执或到期均不构成真实事件的修复或关闭证据。

已具备的链路为：根文件系统真实 `check_resources()` → 认证固定快照入口 → 无参数 TAT → runner 非零 → GitHub workflow failure。2026-11-23 的认证安装与手动 daily 成功记录见演练附件；本设计不把该健康运行解释为真实事件、通知送达或持续闭环已经验收。

继续采用[维护手册](maintenance.md#资源告警候选)的阈值：磁盘使用率及 inode 使用率达到 80% 为 warning、90% 为 critical；非保留可用空间不超过 2 GiB 为 warning、不超过 1 GiB 为 critical。任一 warning/critical 都失败，三维度全部低于 warning 且可用空间大于 2 GiB 才具备资源恢复条件。不自动清理资源，不通过改阈值消除告警。

## 发现、责任与通知

| 环节 | 责任与运行约束 | 必需证据 |
|---|---|---|
| 自动发现 | 原 daily 及其他实际执行的认证快照读取真实根文件系统；不新增 cron 或高频轮询 | run ID/attempt、读取阶段、认证调用证据、稳定失败码 |
| 通知 | 沿用 GitHub Actions 既有通知；接收账户须与实际 schedule 通知归属核对 | 对应失败 run、渠道、维护者实际接收记录；workflow failure 本身不等于送达 |
| 人工兜底 | 仓库所有者按现有每日维护检查查看 Actions、未闭合事件和最近成功运行；通知未到也可由此发现事件 | 巡检时间、最近预期运行与实际结果、缺席或未接手的记录 |
| 接手与处置 | 仓库所有者负责，Agent 仅在任务授权内协助诊断或执行明确方案 | 接手记录、诊断结论、处置方案、授权依据与实际结果 |
| 服务影响升级 | 主站不可用沿用 P1 四小时恢复目标；发现凭证或账户失控按 P0 手册处理 | 影响开始时间，无法确定时明确 unknown；当前影响及目标是否满足 |
| 复查与关闭 | 维护者核对恢复证据后明确关闭；仍有未知或真实异常时保持未关闭 | 新鲜真实检查、运行与身份关联、处置结果、关闭记录 |

warning/critical 表示资源紧迫程度，事故优先级由当前服务影响决定。critical 优先排查，critical 降为 warning 仍是告警。读取失败或无效数据表示无法判断资源健康，应保持失败并排查监测链路，不能编造成已满盘或健康。

既有每日采样可能延迟，不能据此承诺从故障发生起在分钟级发现或接手；主站四小时恢复目标也不证明 daily 提供了四小时内发现能力。本文沿用个人维护模式，未新增全天值班、固定接手时限或备用接收人。所有者无法响应时事件保持未接手；需要额外人员、响应时限或通道时另行决定，不能记录成已有保障。

自然 schedule 成功与手动失败送达可按演练附件既定口径组合为原清单证据，但不能表述为已实测自然定时失败通知。实际事件是否收到，须记录该事件的真实接收结果。通知丢失、GitHub 停调度或整个平台不可用时，本通道没有独立自动告警；每日人工检查是既有责任下的发现途径，未执行的巡检也不得假定成功。

## 事件标识、归并与证据

资源事件以已登记生产目标的根文件系统为范围。磁盘使用率、可用空间与 inode 的异常归入同一未关闭资源事件，保存各次实际报告的稳定码，不因 warning 变 critical 或失败维度变化生成替代事件。传输、认证、控制状态或证据异常单独记为监测链路事件，可以阻塞资源事件恢复验收，但不能冒充资源阈值异常。

首个已验证真实失败建立 `incidentId=resource-<runId>-<runAttempt>`；同一 run 的多个读取阶段作为独立观察归入该事件。每份观察由 run ID/attempt、phase 与认证调用证据摘要唯一关联；重复导入同份证据幂等，不增加新事件、不再次伪造接收记录。人工直连先发现并核实真实异常时，使用 `resource-manual-<32位随机十六进制ID>` 立即建立事件，关联已有管理会话的私有证据摘要，workflow 关联记为 pending；后续补入实际运行证据，事件 ID 保持不变，不编造 run ID，也不为补齐标识制造生产故障。

同一范围已有未关闭事件时追加观察；最高已见级别保留，另记录最新已知级别。当前 producer 只报告一个优先失败码，因此观察是部分诊断，不能推断未列出的维度正常；只有完整真实健康检查能证明全部维度通过。演练诊断使用 drillId 单独归档，不纳入真实事件归并，即使它与真实事件出现在同一 run。重跑会产生不同 attempt，原失败和通知记录均保留。

身份与读取阶段复用演练附件的三种身份及 `bootstrap`、`before`、`after`、`monthly-final`。真实资源错误可能在核验活动 release 和账本之前出现；schema 1 失败封套没有这些身份，事件将站点身份、账本和运行时状态记为未独立核实，不能复制上一成功值充当本次证据。目标来源仍须由认证 TAT 的固定 command/instance 确定。

### 真实失败的回执契约

真实 producer 继续输出严格的 `{schema:1, resourceFailure:<白名单码>}`，不为资源故障追加模拟身份或要求真实故障通过健康前态。runner 在每次通过认证传输并校验封套后，追加一条结构化真实诊断；不能将诊断只转换为异常字符串。`resourceObservations` 为 run 回执中的必填数组，没有合法真实资源诊断时为空；它与 `drillObservations` 分开保留。

每条真实诊断精确包含 `phase`、`resourceFailure`、`level`、`scope`、`receivedAtUtc` 与 `transportEvidenceSha256`。phase 沿用四阶段枚举，resourceFailure 必须在现有 `RESOURCE_FAILURE_CODES` 中；level 由阈值码映射为 warning/critical，读取或数据错误为 unknown；scope 固定为已配置生产目标的 `root-filesystem`，不接收封套提供的任意目标。receivedAtUtc 来自 runner 本次认证接收结束时间，不冒充服务器资源采样时间；旧封套没有 observedAtUtc，其新鲜度继续由本次 TAT 调用及耗时边界证明。认证调用证据摘要按附件的最小记录计算。

对应失败 check 附 `resourceObservationSha256`，指向该诊断的规范字节摘要；run 级数组按发生顺序保留所有条目。首次 bootstrap 异常、bound_probe 前后捕获、月度末尾捕获及 runner 顶层失败处理均须合入同一运行内收集器，再由 public_receipt 白名单输出。`serverReadEvidence` 同时登记该次已认证的失败读取。只要此前有真实失败，之后的健康、模拟失败或其他异常都不能擦除它，最终 run 仍非零。

无效封套、来源不符或传输失败只产生固定监测错误码，不能生成合法 resourceObservations。回执写失败仍显式非零，记录“失败已发生但完整证据缺失”，阻止按该回执完成恢复或关闭。本地候选 runner 已实现这些结构化字段；既有线上运行不因本地代码通过而被解释为已具备该契约。

## 事件状态与人工持久记录

首版以 `docs/progress.md` 的脱敏事件记录追踪生命周期，按现有文档和 Git 交付流程保存；不要求 workflow 写仓库、自动建 Issue，服务器受限入口继续只读。记录尚只在本机时标为待持久交付；任务中断后发现记录未交付，必须从原失败 run 和工件恢复并核对，不能宣称事件记录已具备远端持久性。GitHub 原工件的十四天保留只是取证窗口，需及时保全用于接手和关闭的最小脱敏证据。

| 状态 | 进入条件 | 后续规则 |
|---|---|---|
| `open` | 已发现真实异常并建立事件 | 记录通知 pending/received/not-confirmed，等待维护者接手；未收到邮件不阻止响应 |
| `acknowledged` | 维护者明确记录已接手及时间 | 接收通知与接手分别留证；接手不能把后续监测改绿 |
| `investigating` | 开始只读诊断，记录当前影响与假设 | 不明原因保持 unknown，不据容量告警推断日志或某个 release 为根因 |
| `mitigating` | 执行已授权的明确处置方案 | 逐次记结果，失败仍保留；需要新权限或破坏性操作时按既有门禁处理 |
| `verifying` | 处置结束，或确认无需变更且准备重新取证 | 所有计划内资源写操作结束后再启动恢复检查 |
| `recovered` | 恢复检查及在途证据核对均通过 | 等待维护者完成影响、原因和剩余风险记录；新真实失败返回 investigating |
| `closed` | 维护者明确核对证据并关闭 | 后续复发建立新事件并关联原事件；历史迟到证据仍须追加与判定 |

允许从 investigating 直接进入 verifying，例如异常已自行消退；须记录未执行变更及已知解释，不能伪造修复操作。notification 状态与事件状态独立；人工巡检发现并处理的事件可以在通知未确认时恢复资源，但必须保留通知缺口及独立未完成的通道修复记录，不能把“闭环整体合格”记录为已通过。

每个事件记录至少包含：incidentId、范围、当前状态、首个与最近失败观察、最高/最新级别、全部已保全观察索引、通知接收状态与证据、接手时间、影响与优先级、诊断及未知项、处置方案和授权依据、每次处置结果、恢复运行/回执及身份核验、在途核对结果、关闭时间与结论、复发关联。尚未知的字段明确标记 unknown；不得用空值暗示正常。

状态变化按时间追加，旧失败及旧结论不覆盖；若当前摘要与历史冲突，以完整证据核对后追加更正。每日维护检查扫描 open 至 recovered 的记录：未接手则提醒所有者在本次人工会话确认，已接手未恢复则记录下一步与下次复查时间；不能仅因又收到一次相同邮件而推迟原处置。单人模式下没有自动向第二人升级或提醒服务，所有者未巡检、未响应或未填写下一步均如实保持缺口。

公共记录只放事件 ID、阶段、状态、稳定码、公开 run URL、必要源码/回执摘要与泛化诊断结论，沿用现有运维进度的 Git 历史保存方式。具体容量、设备/服务器路径、云资源标识及原始诊断输出仅用于原有管理员私有取证，不提交到仓库或工件；不读取日志正文或新增访客数据采集。

### 人工事件记录入口与本地样例

实际事件仍由维护者在 `docs/progress.md` 追加记录，初始明确“本地待持久交付”，经已授权的 Git 流程交付后才记为已持久保存。以下是字段模板，不代表本轮发生了真实事件：

| 记录组 | 必填内容 |
|---|---|
| 标识与现状 | incidentId、root-filesystem 范围、状态、最高/最新级别、首次与最近观察索引；未知项写 unknown |
| 发现与通知 | run ID/attempt/phase、回执与认证证据摘要、通知 pending/received/not-confirmed 及实际接收证据 |
| 接手与调查 | 维护者接手时间、影响与优先级、诊断、尚未知原因、下一步与下次复查时间 |
| 处置 | 方案、授权依据、各次结果；无变更时说明自行消退或无需动作，不编造修复 |
| 恢复 | 停用事实（若有演练）、在途归属、新 daily、三次认证读取、源码/站点/运行时/账本核验与实际保全字节索引 |
| 关闭 | 服务影响结束、观察已归属、授权与结果可追溯、原因/剩余风险、维护者关闭时间；通知问题独立未关闭记录及复发关联 |

`ops.monitor.resource_incident.IncidentJournal` 仅是上述人工记录的本地校验与 fixture 模型，不是事件服务，不被 workflow 自动调用，也不自动写仓库或关闭事件。它保留追加历史及观察原文，区分通知与接手、最高与最新级别，允许用 `snapshot()` 保全脱敏字节，再由 `restore()` 重放恢复；已有 recovered/closed 结论重放时必须提供对应的完整恢复回执，缺失或摘要不符即拒绝。真实运维仍须按实际授权、影响与私有证据核验，模型中的人工 proof 标志不替代这些证据。

本地校验模型的恢复证据约束如下：

- 进入 verifying、完成在途核对后，以 `recovery_context()` 取得当前事件完整快照的摘要，记录为 proof 的 `incidentContextSha256`；事件 ID、观察、核验轮次或核对记录变化后，旧 proof 即失效。历史重放按原追加时间及顺序重新计算摘要。
- daily 的 `observedAtUtc` 不得早于本轮 verifying、最近非历史观察或在途核对的记录时间，`completedAtUtc` 不得早于采样开始。同一事件不得再次消费已用于恢复的回执摘要或 run ID/attempt；重新绑定 proof 也不能复用它们。时间检查是本地必要条件，实际调用顺序仍须依据私有证据核对，不能用跨主机墙钟替代。
- `recover(receipt, proof, baseline=...)` 和 `validate_recovery()` 必须取得对应完整基线，核对其摘要及站点身份，并要求检查名称唯一、集合与基线所需的完整 daily 精确一致：DNS、全部制品文件、全部页面、各协议/主机/重定向路径、robots、sitemap、隐藏路径、未知 Host，以及两次服务器核验和项目注册表。删项、重复项、替换项或错误基线均拒绝，即使计数和回执摘要已同步更新。
- `restore(..., recovery_receipts=..., recovery_baselines=...)` 分别按回执及基线摘要索引已保全字节；缺少任一归档则不能重放恢复结论。旧 proof 缺少上下文绑定时拒绝，须重新取得本轮健康与核验证据。

`test_resource_incident` 以受控 statvfs 的真实 schema 1 分支示范异常→通知/接手→处置结果→新鲜健康→关闭，以及中断后从 0600 文件恢复、critical 降 warning、未完成动作、缺失数组、错误身份、在途不明、历史迟到、复发和仅 disarm 的反例。样例不创建真实事件，也不把通知未确认的资源恢复记为整体闭环通过。

## 诊断、控制与处置

1. 核对失败 run 的 event、attempt、固定命令与实例来源、实际错误类型及最近健康证据；存在演练时先区分真实码与模拟码，真实错误不归入演练成功。
2. 先检查服务影响，再用已有管理通道在本机读取根文件系统容量及 inode 元数据、挂载身份、已知维护任务和文件增长情况。输出仅留私有会话，公网与共享回执只报告级别和稳定码；检查日志元数据不等于查看其正文。
3. 依据证据确定处置对象和安全范围。容量不足可审查已有日志保留流程、已批准的 release 退役、备份保留及进程持有的已删除文件；没有证据时不直接选择清理。状态损坏、未知文件或租约/锁冲突时保留现场。
4. 对明确方案先核对当前身份、授权与恢复条件。删除只能走既有保留/租约/退役协议，服务重启、配置变更、扩容和费用分别依授权执行；不得以本设计为无限制清理或购买授权。若主站受影响，按维护手册的故障恢复优先级处理。
5. 记录每次动作和结果，取得新的真实资源状态。阈值仍失败、监测链路不可信或服务未恢复时保持事件未恢复，安排下一次复查；不通过改阈值、禁用监测、删除失败记录或确认旧维护失败来制造正常。

ACK、归并和事件关闭只影响人工事件记录，不屏蔽真实资源检查，也不阻止后续 workflow failure。每次执行仍按当前实际情况报告，保留 GitHub 自身可能产生的重复通知；不承诺应用级自动去重或重发。通知未收到先排查账户设置、schedule 归属及平台状态，在人工会话继续处置资源问题，保留通知链路缺口。

## 真实恢复与迟到结果

真实事件没有 disarm。进入 verifying 的前提是本轮资源处置已结束、没有计划中或仍执行的清理/重启等动作；若恰有演练则另按附件完成停用及在途核对。仅撤销演练不能证明真实资源恢复。

操作会话核对处置前及处置期间的在途 TAT、SSH 和 workflow。先取得可验证终态及实际证据，再新发起 fresh daily；不能因一个旧 run 后来成功、任务被取消或某份输出在邮箱中较新就判断恢复。新 daily 的三次服务器读取均须认证、健康，resourceObservations 与 drillObservations 均明确为空数组，正常 snapshot 及身份/账本一致性、公网检查也须通过。缺回执、缺少必填字段、任一资源仍 warning/critical、读取或认证异常均阻止 recovered。

将恢复 run ID/attempt、workflow 源码 SHA、回执摘要、关联认证读取证据、已验证站点/运行时身份与账本核验结果记入事件；证据摘要须能回查实际保全字节。schema 1 初始故障没有完整站点身份时，记录故障身份未知、恢复时新取得的真实身份及期间已核实的变更，不虚构“前后相同”。若存在合法发布或运行时变化，须记录变更及其验收，不能以身份变化替代解释资源为何恢复。

恢复后到达的旧失败不能丢弃：能以实际调用、阶段及已核实顺序证明早于恢复采样的，追加为历史观察；发生在恢复采样后则重新调查，已关闭时作为复发新建并关联；顺序无法证明时保持待核对，不能用跨主机墙钟估计为历史。演练产生的迟到邮件按 drillId 归档，不重新打开真实事件。资源临时回落后再次跨阈值，也不能因已接手或曾成功而被抑制。

closed 要求维护者明确核对：真实恢复条件、服务影响结束、在途观察已归属、处置及授权结果可追溯、原因与剩余风险如实记录，并为未解决的通知或监测问题保留独立未关闭记录。原因尚未知可在记录其风险和后续调查事项后关闭已恢复的资源事件，但不能宣称根因已消除。

## 实现拆分与独立验收

| 单元 | 主要不变量 | 前置与行为证据 |
|---|---|---|
| 1：真实失败证据 | 任一读取阶段的真实异常均使 run 失败并保留定位信息 | 复用附件的认证证据及各阶段传播设计；以无 drill 的真实 schema 1 资源分支，覆盖磁盘/inode、warning/critical、读取错误、额外字段、真实与演练并存及回执写失败 |
| 2：事件记录与接手 | 重复或后续成功不能擦除未闭合事件 | 依赖 1 的脱敏 fixture；验证同范围归并、级别升级、部分诊断、通知与 ACK 独立、人工记录中断后恢复、复发新建关联；不依赖生产故障 |
| 3：真实恢复与关闭 | 只有新的真实健康证据和人工核验可关闭事件 | 依赖 1、2；用可控输入完成真实错误分支的异常→ACK→处置结果→新鲜健康→关闭，覆盖 critical 降为 warning、错身份、无效回执、在途迟到和“仅 disarm 就关闭”的反例 |
| 4：真实通知与持续运行 | 通知送达及实际调度均有独立证据 | 依赖前三项、review、精确 CI 与认证安装；按附件安全演练并确认实际接收，保留自然 schedule 和实际每日人工巡检记录 |

真实分支测试使用受控 statvfs 输入进入与生产相同的真实失败判定及 schema 1 接收分支，不能只测带 simulated 的 schema 2。通过 fixtures 证明真实事件状态转换，再用服务器合成演练验证实际 TAT、runner、通知和恢复；不得为验收而填满生产磁盘或 inode。发生自然真实事件时按本文处理并留证，但不把等待生产事故当作交付前提。

人工事件记录可先用 fixture 演示独立验收，无需提前新增事件状态服务或自动化写入工具。实现前仍须完成专项 review；本轮设计不等于新字段、状态传播或演练入口已上线。

## 完成标准与现有缺口

#88 资源告警单元的闭环合格要求：既定阈值与真实失败分支验证、四阶段失败证据传播、可恢复的人工事件记录及接手/处置规则、真实恢复与迟到观察反例、认证生产接线、安装后的自然 schedule，以及按附件取得的两轮失败通知/恢复证据和维护者接收确认。资源恢复可与通知问题分别记录，但存在未验收通知通道时不能勾选整体闭环完成。

运行缺席和通知故障的独立自动告警、全天值班与分钟级发现仍不在既有能力内。本地新增契约与人工事件样例已形成候选，持续巡检、生产认证安装及通知送达仍待独立验收；Issue #88 其余日志、备份与组合维护单元独立推进。本轮未创建真实事件、执行生产变更或发送通知，未新增第三方服务或访客数据处理。实现与检查记录见[本轮进度](../progress.md#2026-11-23--88-告警闭环本地实现)。
